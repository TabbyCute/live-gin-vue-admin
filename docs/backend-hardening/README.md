## 性能解释

本机同时运行Docker与其他应用，以下只能用于定位实现成本，不能换算“支持多少在线用户”，也不是生产SLA。

- 日志热路径与旧HEAD实现对照：约89–99µs/次降到1.9–2.2µs/次，分配4696B/33次降到200B/4次；另一次旧实现342µs是明显波动。仅日志组件结果，非整体接口吞吐提升。
- 26001条模拟来源收益事实、131个账户版本：92条SQL、约0.873秒；该大规模用例使用专用SourceVerifier。另有130笔真实钱包→礼物→收益来源+一次退款的跨页完整验证及旧页篡改拒绝，不能混报为26001条真实礼物性能。
- 1000条银行账单导入约187ms、核对约101ms；只有小规模平台attempt，不能当作生产账单规模承诺。
- 钱包流水读取400次/并发16：本次约1878次/秒，P95 13.37ms；单一热点钱包100笔礼物写入约38次/秒、P95 2.48秒。财务串行锁保留，不能把热点串行写与多钱包总吞吐混算。
- 500条收入事实、64笔提现/并发16：P95 1.832秒，金额校验全通过；64个ready出款单P95 1.571秒且余额不变。20笔人工付款复核入账P95 114.5ms、冻结归零，外部银行调用0次。
- 在线状态1000次热点open P95 8.14ms、心跳P95 6.92ms；这两组隔离了认证SQL，只测Redis状态机，不是HTTP端到端延迟。16房间160次open P95 19.07ms。完整负载日志见[evidence/load.log](evidence/load.log)。

## 发布与未关闭事项

数据库变更与应用发布分开。新应用启动只读校验这三块schema；先完成增量迁移，再发布应用。回滚旧应用时保留新表、幂等记录和审计，不清表、不覆盖生产资金。所有测试结果只覆盖当前本地环境。

不能据本报告宣称“顶级企业生产环境认证”。此前P0的真实短信验证仍未关闭：现有注册使用配置内共享验证码，不能证明手机号归属；本轮按P1/P2范围没有将它包装成真实短信能力。仍需真实支付渠道与IM契约验收、业务目标负载/尾延迟与恢复目标、生产规格容量演练、持续外部告警及备份恢复运营。真正可信的O(增量)收益检查点尚未实现；在依赖历史源可变时，不能用缓存余额绕过全历史核验。历史量增长仍可能触及在线8秒预算，后台30秒审计也不会放宽资金核验。

安全扫描仍保留MCP无修复版本的可达告警（已有同源限制缓解）及旧admin编辑器/编译器/图表链告警，详见依赖文档。事件永久记录的归档、旧来源补扫持续积压、真实银行更正流水/跨日与合并付款等边界需按业务扩展另行验收。root自审例外是保留的既定产品规则，审计仍记录实际操作人。
