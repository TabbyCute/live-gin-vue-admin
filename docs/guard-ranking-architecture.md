# 模块划分与本次优化评估（2026-11-04）

当前分层与同库模块化单体适合现阶段，没有发现需要整体推翻或立即拆微服务的问题。资金操作使用同库事务，贸然拆成远程服务反而需要新增分布式记账、补偿和一致性维护。本次保留 Router → API → Service → Model 和各层 enter.go 注册方式。

| 模块 | 应负责的事实 | 本次处理 |
| --- | --- | --- |
| live/social | 账号、主播、直播访问和公开资料 | 复用批量公开 DTO 与房间访问控制，不复制用户敏感字段 |
| wallet | 用户 COIN 余额、扣款、退款、连续流水 | 不改余额内核和接口；真实充值/扣退款纳入回归 |
| gift | 消费、退款、分成快照、权益命令 | 同事务追加守护授予命令，事务外履约；不直接写守护表 |
| guard | 方案、分来源权益、补偿、到期与重建 | 新独立模块；用结构化命令接入，永久幂等、租约和来源重算 |
| ranking | 原始礼物净值的可重建投影 | 新独立模块；与财务交易解耦，影子代际、漏记检测、批量 SQL |
| earning | 收益事实、兑换、结算、可提现账户、提现冻结与复核 | 保持原有单一收益事实入口，不把附赠守护再记一份收入 |
| payout | 收款资料、公司出款、尝试、确认及最终记账 | 保留已有实现和独立权限，本次不接真实支付渠道 |

## 解决的主要维护问题

1. 原守护仅在 gift 中留接口，直接继续堆叠会使订单事务同时承担权益生命周期。本次独立 guard，Provider 合约放在公开模型边界，guard 不反查 gift 或调用 wallet。
2. 原 `/gift/ranking` 是财务聚合页面，直接让 APP 高频查询会混合统计/权限职责。本次新投影独立服务和 DTO，旧接口保留；新财富/魅力不引用主播分成。
3. 为减少重复安全代码，新模块复用 internal/modulekit（精确权限、事务重试、错误）与 internal/httpkit（严格绑定、请求预算、有限限流）。没有批量改写历史资金 API，避免扩大回归面。
4. Schema 核验对 MySQL 使用批量 information_schema 查询，校验列类型/可空性、唯一索引、CHECK 与不可变触发器。兼容发布在新表完全不存在且守护销售关闭时可继续提供旧功能；部分迁移不兼容会拒绝启动。
5. 重建不清历史、不删除去重记录。APP 从显式公开 DTO 返回字符串金额，管理员修改使用永久请求号和审计。

## 需要持续治理的边界

- 初始化层负责组合模块。新增“守护直购、粉丝团、充电、大赏”等先建立各自业务订单和来源适配器，再调用 wallet/earning/guard 公共边界；不能直接修改余额或从客户端提交收入金额。
- worker 的吞吐、积压、最长延迟、失败次数必须监控。排名源端用 anti-join 收据补晚提交，源数据非常大时需在目标环境评估执行计划和历史核验窗口；不能只看 checkpoint 最大 ID。
- 当前单会员重放上限为 10000 条授予+补偿事实，超过时失败关闭；后台同步榜单核验上限 10000 个事件，避免无限占用管理请求。大规模运行前需要分段快照/异步审计任务扩容，不应将这两个边界描述为无限容量。
- 旧榜单 UTC、新榜单 Asia/Kuala_Lumpur 的差异已明确写入契约。不能悄悄切换既有报表口径；更改新榜单时区需单独版本化迁移和全量重建。
- 前端共享依赖的既有告警与生产 HA/RPO/RTO、长时间压测、跨实例网关限流仍是独立上线验收项，见测试文档。模块测试通过不等于全站通过生产安全认证。
