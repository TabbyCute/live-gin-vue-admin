# 主播守护（2026-11-04）

守护是独立的权益模块。用户通过赠送已开启守护附赠的礼物获得权益；本期没有直接购买守护、购买价格或支付渠道。

入口：[18 项交付报告](delivery-20261104.md)、[APP/后台接口](api.md)、[发布和生产核验](deployment.md)、[测试结果](testing.md)、[模块划分评估](../guard-ranking-architecture.md)。当前交付状态以部署记录为准，表已迁移不等于应用已发布或礼物已开售。

## 数据与状态

| 表 | 职责 |
| --- | --- |
| guard_plan | 方案、等级、展示优先级、建议天数、公开权益配置、启停、排序与版本；没有价格，永久编号禁止改名或删除 |
| guard_membership | 用户+主播唯一的可重建投影；保存来源时间段、最高生效方案、下个转换时间和不可变流水引用 |
| guard_grant | 原始来源、用户/主播、方案快照、原始天数；来源字段不可改删，补偿时长/到期/状态为可重建缓存 |
| guard_compensation | 唯一退款来源、对应授予、原始命令快照、申请撤回时长；只追加，允许先于授予到达 |
| guard_ledger | grant/renew/compensate/expire/rebuild，前后快照、实际时长变化；禁止更新/删除 |
| guard_task | 永久任务来源、租约令牌、重试次数、退避时间、脱敏错误和完成时间；异常到期也留记录 |
| guard_admin_permission | 当前角色的完整路径+HTTP 方法授权 |
| guard_audit_log | 请求键、操作者、请求快照、结果；永久幂等与不可变审计 |

一个自然日按 86400000 毫秒计算。同方案按来源顺序续期，不同方案独立保留时间段，同时生效时展示快照中优先级最高的方案，同优先级按方案编号排序。停用或修改方案只影响新配置和新交易，已有权益保持原快照。

例：来源 A 从第 0 天生效 3 天，来源 B 续期 1 天。第 0.5 天退款 A 的 2 天，A 保留至第 1 天，B 顺延区间变为第 1～2 天。若第 2 天才全退 A，只能撤回 A 剩下的 1 天，已使用的 2 天不会被抹掉。流水记录实际撤回量，补偿单保留原申请量。

## 与礼物的闭环

1. gift 同事务校验方案，保存方案/每件天数/总天数快照，扣钱包、记订单和收入/收益，并插入 gift_benefit_grant。
2. 事务提交后，独立 Worker 领取任务，再调用结构化 GuardService.Fulfill。guard 不反查礼物表，永远不调用钱包。
3. guard 在会员行锁内追加永久唯一来源、重算权益和写流水；成功后 gift 确认履约。
4. 退款事务原子完成钱包退款、负向财务事实和 gift_benefit_compensation。独立 Worker 调用 Revoke，按原来源只撤回未使用部分。
5. 权益先提交而成功响应丢失，重试相同 GrantNo/CompensationNo 不会重复发放/撤回。补偿先到时保存来源快照，后到的授予必须匹配该快照。
6. 到期任务按 NextTransitionAt 批处理并锁会员二次检查。重复扫描不会追加重复到期流水；到期后也可能切换到仍有效的较低等级。APP 按服务器当前时间计算，不能靠 Worker 延迟延长权益。

授予/补偿任务租约 60 秒，调用 25 秒；完成必须匹配 lease_token。失败按指数退避，最大 5 分钟，20 次后等待管理员核验/重试。到期处理是短数据库事务，以会员锁复查实现多实例互斥；失败单独留任务并退避，不阻断其余会员。所有来源保持永久唯一，重试不靠 Redis 锁。

读取会员时批量对比不可变流水快照。正常授予、补偿或到期发现投影损坏会失败关闭；只有受控重建入口允许按事实修复，修复也追加审计和流水。

未来新增 wallet_purchase 时新增独立购买订单/适配器，沿用 grant/compensation 的通用 source_type/source_no/source_entry_no 与权益重算核心；不改会员、来源或补偿表的结构。
