# 新增客户端业务分模块评估

评估日期：2026-11-09。范围为注册至主播人工出款，以及直接支撑该链路的直播、社交、权益、榜单和运行设施；不扩展为通用管理后台重构。

本次在既有代码、模块说明和本轮测试证据上分模块复核，不新增生产测试账务，不执行真实转账。用户已提供服务器访问方式，但尚未 SSH 连接、部署或现场验收。原始测试记录中的“尚未提供部署入口”是当时状态，以本说明为准；本文件不保存访问凭据。

## 结论与证据口径

资金内核、业务幂等和人工出款状态机的测试证据较充分，可以进入预发及受控业务验收。公开生产交付仍被真实身份验证、人工付款外部核对、安全修复实际发布和运行恢复验收等缺口阻断。不能用测试数量代替生产签收，也不能用系统内 paid 状态证明银行到账。

- **代码/隔离验证**：普通 Go 回归 658 个测试及子测试通过，129 个场景跳过；另行启用 MySQL/Redis 的专项套件通过。执行过竞态检测、13 个短时定向 fuzz、构建与静态检查。H5 57 项、管理端 58 项逻辑测试通过。这些数字不代表全部可能场景或完整覆盖率。
- **连续业务链验证**：新注册、登录、主播申请、充值、送礼、收益结算、选收款账户、提现、人工复核到 paid，实际 Service 在 SQLite 与真实 MySQL 下通过；直播已发布状态及银行回单为隔离测试数据，没有真实媒体推流或银行转账。
- **远程证据**：正式数据库 wallet/gift/earning/payout/guard/ranking/presence 七组结构只读检查通过，资金摘要未变，本轮无迁移。公网低影响探测已做；SSH 运行环境、浏览器交互、真实短信及银行到账未验收。
- **判定含义**：“进入预发”表示具备继续验收的代码基础；“有限规模”表示存在已知扩展边界；“上线阻断”表示公开生产所需条件缺失；均不表示模块已在线上通过。

## 1. 账号注册、登录、密码与会话

**判定：认证基础可进入预发；真实手机号验证为公开上线阻断项。**

- 已验证：重复注册、并发唯一性、错误密码、封禁、旧凭据失效、越权和并发改密。已增加账号维度限流、哈希运算并发控制、请求预算；密码哈希在资金/账号行锁外计算，锁内复查账号及凭据版本。
- 明确缺口：短信接口只等待后返回，注册使用共用超级码，却写入手机号已验证时间。当前字段不能证明用户拥有该号码。
- 优化与验收：接入真实验证码发送、一次消费、有效期、错误次数和重放保护；按号码/IP/设备控制发送成本，验证服务商超时、重试及回执。号码更换、找回密码和会话撤销应有完整流程。
- 排障：记录发送业务号、供应商请求号、结果码、耗时和脱敏号码；不得记录验证码、密码或完整 token。现有通用 trace 不能替代短信供应商关联信息。

## 2. 主播申请、审核、权限与直播生命周期

**判定：业务状态可进入预发；真实媒体运行尚未验收。**

- 边界：主播审批通过不等于已完成实名认证；现有提现规则明确不校验实名认证、主播认证或收款实名，不应把这些能力写进交付承诺。
- 运行缺口：真实 SRS 回调来源限制、推播放鉴权、断网恢复、SRS 重启、转码/CDN 带宽和播放延迟未做现场验收。服务层状态测试不能给出媒体容量结论。

- 排障：场次号、主播号、SRS 实例/代次、状态迁移原因、重连次数、终止重试和耗时应可关联；专项 Hook 日志应接入 trace 并审计脱敏。

## 3. 社交关系、访问控制与观看历史

**判定：可进入预发；热点主播计数需要容量规划。**

- 已验证：关注/取消、屏蔽与访问限制、旧版本覆盖防护、观看历史异步聚合、队列有界、租约竞争、Redis 故障和重试恢复；专项套件通过。
- 性能证据：本机隔离测试中，热点主播关注切换在 32 并发下 P95 约 1,075ms。聚合心跳吞吐约 2,844 次/秒，但这不是生产在线人数容量。
- 优化方向：测量热点行锁等待，再评估分桶计数、批量更新和可重建投影。权限撤销仍应及时生效，展示计数允许的延迟需先定义。
- 排障：积压长度、最老待办年龄、刷新失败、租约失效及隐私撤销失败要有指标和告警，不能只统计 HTTP 成功率。

## 4. 在线人数、游客、心跳、点赞与观看时长

**判定：可进入受控预发；恢复与集群容量尚未验收。**

- 已验证：签名游客/会员、重复设备去重、心跳乱序、超时离线、点赞授权、SQL 检查点、租约及代次隔离、Redis 丢失后受控恢复。未知在线状态明确标 stale，避免伪造为零。
- 性能证据：隔离测试 1,000 次心跳/32 worker，P95 约 7.18ms；多房间查询 P95 约 11.10ms。
- 扩展边界：当前全局 admission 在 Redis 单 slot，可能成为扩容热点；必须通过多实例和真实房间分布压测验证。不能仅增加 worker 数量。
- 验收与排障：进程异常退出、滚动更新、Redis 重启/全丢失、队列满、SQL 恢复后的统计一致性；监控 stale/dataLost、检查点滞后、队列拒绝和最终落账失败。

## 5. 钱包、人工充值、消费与退款

**判定：账务内核测试较充分，可进入预发；充值外部资金核对另行验收。**

- 已验证：整数金额、余额与连续版本、不可变流水、永久业务幂等、审核与日额度原子提交；并发扣款/退款、退款不超原金额、未知提交结果、故障回滚和结构约束漂移。
- 性能证据：流水查询约 2,297 QPS/P95 10.13ms；单钱包竞争扣款约 115 次/秒/P95 426ms；分散到 16 个钱包约 625 次/秒/P95 71ms。均为隔离环境实测。
- 边界：目前充值为人工入账，并非支付渠道收款确认。普通管理员双人审核；ID 1 root 自审是既定业务特例，不应宣称全员强制双人控制，也不在此次评估中擅自更改规则。
- 优化方向：保留金额串行校验及事务锁，按用户分散写入；新增支付渠道时复用统一账本，补渠道订单、验签回调和外部账单核对，禁止直接更新余额。
- 排障：业务号→交易号→流水号→版本→审核审计；告警关注锁等待、死锁重试、幂等冲突和余额/来源核对失败。

## 6. 礼物、分成规则与退款

**判定：正确性可进入预发；热点发送与消息履约需验收。**

## 7. 守护权益、续期、退款补偿与到期

**判定：代码及隔离验证通过，尚不具备直接开启售卖的运行证据。**

- 已验证：同方案续期、不同等级独立、来源永久去重、退款仅撤销对应来源未使用时长、到期、并发补偿、可重放重建和后台租约恢复。
- 发布边界：按当前记录，生产售卖开关仍关闭。必须确认结构、方案、Provider、履约/补偿/到期 Worker 和一致性状态后开启。

## 8. 礼物榜、财富榜与魅力榜

**判定：投影模型可进入预发；更新时效与大规模重建尚未验收。**

- 已验证：净礼物金额、退款归原周期、时区、精确整数排序、永久来源去重、迟提交补偿、重建代次切换及私密房间访问限制；榜单不修改财务事实。

- 优化与排障：先约定更新延迟目标，再验证百万级历史数据下增量投影、重建切换、分页与索引；监控来源进度、投影延迟、重建进度和源数据差异。

## 9. 收益事实、兑换、结算与欠款

**判定：资金规则可进入有限规模验收；持续高流水扩展存在明确限制。**

- 已验证：来源唯一、分成规则快照、整数换算、跨批次余数守恒、双人复核规则及 root 特例、退款追偿、available/frozen/paid/debt 版本链和账务核对。
- 性能证据：500 个事实、16 并发/64 次提现，P95 约 1,287ms；测试中资金核对通过。
- 扩展限制：每批结算最多 1,000 个事实；同步历史深度核验最多 20,000 个事实，超过会拒绝放行。高流水主播可能先遇到业务阻断，而非单纯变慢。
- 优化方向：建立可审计核验检查点与增量核对，再做大历史量和退款跨检查点测试；不能只提高上限或删掉核验。后续广告/订阅等来源复用统一来源接口和不可变事实。
- 排障：来源号、规则版本、结算批次、币种/兑换比例、余数、负向事实和四余额差异，分别统计核验耗时与锁等待。

## 10. 收款账户、提现申请与冻结

**判定：隔离、加密和冻结流程可进入预发；身份及密钥运行管理需补验收。**

- 已验证：仅本人有效账户可选、AES-GCM 加密/HMAC 去重、默认账户唯一、停用竞态、不可变收款快照、余额冻结与申请同事务。
- 边界：绑定有效不等于银行已认证、姓名匹配或实名完成；当前业务未要求这些判断。是否增加此门槛需要明确业务规则，不能默默改变现有提现条件。
- 风险：高权限完整资料短时单次查看已有控制，但没有 MFA；需验证查看审计、权限即时撤销和密钥备份。密钥轮换必须保留旧数据可解密能力及指纹一致性。
- 排障：收款账户号、快照版本、提现号、冻结流水和 trace；不打印姓名、完整银行卡号、明文资料或密钥。

## 11. 人工出款、回单、未知结果与成功记账

**判定：人工出款状态机较完整；真实银行到账闭环尚未通过。**

- 已验证：唯一出款单/成功尝试、领取、私有加密回单、永久流水防重、独立复核规则及 root 特例、unknown 阻止盲目重试、明确失败取消、成功原子入 paid、终态不可重开。
- 性能证据：隔离 20 单人工复核记账 P95 约 160ms，银行调用次数为 0。只能证明系统记账行为。
- 关键缺口：系统不自动发起银行转账，也没有自动外部银行账单核对；内部对账不能发现所有“系统成功但银行未到账”或外部重复付款。银行回单的上传也不独立证明真实性。
- 验收标准：若采用人工付款，需授权财务完成实际付款、外部流水/到账核对和复核，并演练处理中超时、结果未知、重复回单和隔日差异；无需先开发自动付款才能验收人工方案。未来自动渠道须单独接适配器、验签回调、查询补偿与外部对账。
- 运行缺口：私有凭证目录挂载、磁盘满、写入失败、备份恢复和权限隔离未现场验收；终态事件尚缺完整外部投递能力。需监控 unknown 时长、待复核年龄、证据读写及账实差异。

## 12. H5 客户端交互

- 已验证：57 项逻辑测试，包括金额字符串、幂等请求恢复、账号切换、敏感信息清理、限流响应和 presence；本轮 H5 生产依赖扫描为 0 项发现。

- 优化与验收：真实设备贯通注册→充值展示→送礼→主播提现结果；覆盖超时后原请求查询、会话过期、状态回退和可理解错误提示。资金相关按钮禁重复不能代替服务端幂等。

## 13. 公网安全、数据库、日志与运维交付

**判定：多项代码修复已完成；上线生效和运维验收为阻断项。**

- 已完成本地修复：严格 CORS、可信代理、请求体/读请求/执行预算、认证成本控制、统一服务端 Request-ID、通用日志脱敏、release 隐藏调试入口、依赖就绪探针。
- 已观测线上旧行为：任意 Origin 可被回显且允许凭据，Swagger 可访问，未提供新的统一追踪响应头。修复尚未部署，不能当作线上问题已经关闭。
- 远程数据库：七模块结构及持久性参数通过只读核验，本轮无需迁移；应用账号仍有 DDL 权限。拆分运行与迁移身份时需验证实际启动校验权限，避免直接撤权导致故障。开发库连接超时仍未核验。
- 凭据管理：prod/dev 配置仍被 Git 跟踪，应做暴露范围核查与兼容轮换，发布包保密存放。收到的 SSH 凭据不写入文档、代码或日志。
- 依赖边界：按本轮扫描，后端仍有 1 项可达 MCP 上游漏洞，已加同源传输缓解但扫描不为零；原管理端依赖有 4 high/9 moderate。管理端通用功能不在本次改造范围，但同部署系统的依赖风险仍需跟踪。
- 现场缺口：已知入口是 HTTP，其他 HTTPS 域名/网关情况未知；待核验 TLS、可信代理、网络白名单、日志轮转/留存/访问权限、私有目录、服务身份、进程托管、回滚、备份恢复和主从故障切换。
- 可观测性缺口：统一 trace 与健康探针只是基础，尚未证明指标采集、告警送达、值班响应和恢复流程有效。需要按请求失败/延迟、DB 池/锁等待、Redis/worker 积压、财务差异和 unknown 出款分级告警。

## 执行优先级与签收条件

1. **P0，公开生产前**：落实真实手机号验证；发布并复验本地安全修复，核验真实域名/TLS/代理；完成敏感配置与私有凭证存储核查，处理 Hook URL 日志风险；按人工付款方案完成一次可审计的外部资金核对及异常演练。恢复方案和备份可用性需有实际证据。
2. **P1，扩量前**：定义目标请求量、活跃房间分布、P95/P99、错误预算及恢复目标；在接近生产的环境做热点/混合负载；建立收益核验检查点，验证 worker 多实例和 Redis 恢复；接通日志、指标和告警。root 特例保留既有产品规则，建议用应急使用、审计告警及账号保护控制风险。
3. **P2，业务拓展**：新增收入来源与渠道适配；完善财务终态事件投递、外部账单导入/自动核对、设备验收与长期回归。自动付款的优先级取决于人工出款量，不应为追求形式上的“企业级”提前复杂化。

所有性能数字只用于定位当前瓶颈，均不是生产 SLA，也不能换算成“支持多少在线用户”。下一轮生产签收应逐项附运行证据、责任人、回滚方法和未关闭风险，禁止把“已打包”写成“已发布”。
