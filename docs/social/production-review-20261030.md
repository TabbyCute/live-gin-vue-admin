# 社交模块性能、安全与可靠性复核（2026-10-30）

本轮复核此前的观看历史告警修复，并继续修复社交请求、队列、鉴权及基础依赖中的具体问题。沿用现有分层、单数snake_case表名和公开用户资料结构；没有新增表、字段、索引或更改DTO。修改只在工作区及隔离测试依赖中验证，未部署、重启线上实例或修改生产数据。推送渠道、短视频/回放和CDN仍属于用户明确排除的范围。

## 1. 发现与处理

| 问题 | 修改 | 验证重点 |
|---|---|---|
| 空历史队列串行探测16个分片，远端往返累积超时 | 保留并复核此前的pipeline探测，只锁有到期记录的分片 | 空队列仅1次pipeline；坏分片不阻断健康分片 |
| 限流150ms、缓存100ms、上报150ms和解锁150ms与远端延迟不匹配 | 必要Redis操作1秒、缓存500ms；限流与Worker状态合并pipeline；小型脚本直接EVAL | 冷脚本及180ms延迟回归，不绕过写限流/背压 |
| go-redis默认不把请求deadline用于socket读写 | 单机与Cluster均开启ContextTimeoutEnabled，初始化Ping限5秒，失败关闭客户端 | 真实TCP代理吞响应，80ms请求预算在500ms断言内返回 |
| 活跃队列32条记录逐条Redis确认 | 成功/失效前缀批量CAS确认，中途失败保留未处理记录 | 前缀部分失败、并发新心跳、租约释放、32条批量往返计数 |

| 缓冲载荷可能与用户/资源key不符 | 消费前核对绑定，损坏项计数并丢弃 | 不写入其他用户，不阻塞后续记录 |
| APP鉴权查询原先不在社交请求预算内 | RequestBudget放在APP JWT之前，5秒context覆盖鉴权和业务 | 真实APP JWT触发账号查询，断言查询deadline及失败关闭 |
| JSON解析只消费首个对象，可能忽略尾部超限/垃圾 | 完整读到EOF、继续执行结构校验，32KiB正文/4KiB query/8KiB Authorization上限；no-store | 已知和未知Content-Length、超长空白、第二对象、垃圾尾部、操作者伪造 |

| SQL日志可能展开观看会话token | 开启GORM ParameterizedQueries；新准入查询使用Find而非Scan | 正常查询/Create/错误Exec日志不包含测试token，实际查询参数仍生效 |
| 运行时和依赖存在公开漏洞 | 固定安全Go工具链，升级命中修复版本并同步构建入口 | 全程序govulncheck复扫、构建、定向回归、XLSX/XZ兼容冒烟 |

SQL日志参数隐藏只作用于GORM支持的参数过滤路径；手拼SQL、驱动原始错误及GORM Raw/Scan记录器不能据此宣称全部脱敏。社交新增的会话准入查询已避开该限制，Worker错误继续仅记录有限分类、阶段、分片和标准错误码，不输出原始缓存、会话或SQL参数。

## 2. 安全与一致性结论

- 所有APP操作者只取JWT；请求中userId无法代操作。匿名社交路由拒绝，私有列表按本人取数；公开用户资料白名单和直播可见性规则保留。
- 关注、拉黑、准确计数、关系版本及Outbox继续同事务提交，counter按用户主键升序加锁，唯一键和有限死锁/锁超时重试保留。
- 请求失败不会为了可用性而跳过授权。Redis故障时敏感写拒绝；读请求仍只有进程级100QPS回源兜底。Worker故障时撤销/删除类隐私操作仍须通过Redis写限流。
- 5秒是可协作取消的业务context预算，不是杀死任意goroutine或慢客户端的硬墙钟上限；HTTP服务器和入口网关仍负责连接/读写超时与匿名流量保护。
- 历史准入增加的是会话资格检查，不改变普通心跳的短期缓冲语义。已删除/替换的旧缓冲可能暂被Redis受理，最终落库重新校验token/version/epoch/sequence，只UPDATE匹配行，不恢复已删除数据。需要持久化确认使用checkpoint。
- 历史处理10秒、CAS确认1秒、解锁1秒，低于15秒租约；租约异常或进程暂停时数据库条件仍兜底。崩溃在提交后确认前只造成重试，不造成旧进度覆盖新进度。
- 管理员撤权在每次请求鉴权时生效；已经通过鉴权的在途请求与后续撤权仍有时序边界。不存在后台用户自动获得私密直播播放权限的规则。

### 最终性能样本

Go1.26.10、真实本机MySQL/Redis，Service层调用，最终测量未与race测试并跑。社交逻辑压测使用受控用户/资源适配器；只有第一行包含真实账号、主播、房间、场次与权限联查。下面均为零错误。

| 真实直播表的100人公开资料关注页 | 400/16 | 1337.25 | 15.15 | 21.72 |
| 100目标关系批量状态，无Redis | 400/16 | 1306.41 | 15.83 | 17.40 |
| 热门同一主播首次关注 | 1000/32 | 129.01 | 261.95 | 279.78 |

注入180ms往返延迟后，冷脚本写限流约188.64ms完成、只发一次pipeline。32条失效记录的确认在30ms往返延迟下约231.16ms完成，共2次pipeline（探测/确认）和4个单命令；不再发送32次单独确认。延迟注入代表受控实验，不等同实际远端网络分布。

新增会话准入SQL的实际EXPLAIN：历史走uk_social_history_resource，counter走PRIMARY，均为const、rows=1；没有新增COUNT、扫描历史列表或额外索引。公开资料查询仍为批量、最多2条SQL；当前场次走PRIMARY，样本执行计划无ALL。其他列表计划受数据分布影响，不能由小样本推断百万关系的优化器选择。完整数值和SQL计划见[原始结果](load-result-20261030.json)。

完整仓库仍存在历史记录中的无关测试问题，见[验收记录](verification.md#全库既有检查失败)。本轮只报告实际运行范围，不把定向测试描述为全仓测试通过，也不承诺任意数据量、任何故障下不丢普通心跳或永久无需维护。
