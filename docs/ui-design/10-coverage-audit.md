# 客户端 UI/UX 覆盖审计报告

## 1. 审计结论

本次审计仅覆盖用户/主播前台客户端，不包含 `web/` 管理后台。已建立 20 个页面清单项（C-P00~C-P19）：1个应用壳、15个核心业务页、1个正式404页、3个占位/演示页；另识别4个调试路由和20个页面内弹层/操作面。正式设计范围为 C-P01~C-P15、C-P19及其操作面。

截至本报告，所有已识别的真实客户端功能均已映射到页面、状态或操作面；所有正式业务页面均有逐页规格和 AI 生成提示；角色、权限、主要异常、跨平台适配及资金写操作的“结果未知”状态均已覆盖。源码无法证明的能力已标为「待确认」或明确排除，没有作为已实现功能写入设计需求。

## 5. 状态和异常覆盖检查

| 状态组 | 覆盖结果 | 重点设计要求 |
| --- | --- | --- |
| 默认/加载/成功/空/失败 | 全部正式页 | 首屏与局部加载分开；旧数据可保留时不清空 |
| 断网/超时/服务端异常 | 全部联网页 | 持续错误用内联Notice；可恢复时提供重试 |
| 刷新/重新进入 | 列表、钱包、直播、开播、收益 | 刷新不重复写请求；重新进入恢复安全状态 |
| 未登录/登录过期/无权限 | 路由和交互两层 | 安全redirect；公开内容不被错误拦截 |
| 账号/主播/钱包受限 | C-P04/05/10/11/12/14 | 明确原因、截止时间、可恢复路径 |
| 按钮/表单/搜索筛选/分页 | 组件规范与逐页矩阵 | default、focus、disabled、loading、error、success |
| 弹层确认/取消/失败 | 全部登记操作面 | 提交失败保留输入；危险动作二次确认 |
| 重复提交/防误操作 | 写操作 | busy锁、幂等键、不可逆动作说明 |
| 结果未知 | 礼物、提现、开播准备、相册写操作 | 保留原键/参数；查询或安全重试；不伪报失败 |
| 业务终态 | 场次、提现、相册审核、主播审核、订单退款 | 状态名称与服务端语义一致 |
| 实时与轮询 | presence、点赞、开播、提现 | 连接失败降级；实时事件后以HTTP权威重查 |

关键语义审计通过：

- `approved` 提现统一为“审核通过·待出款”，`paid` 才是已付款。
- 送礼成功动效只表达本人确认，不证明全房广播。
- Presence 失败显示同步降级，不把在线数伪造为0，也不停止合法播放。
- 钱包只有只读查询，不生成充值、转账或客户端退款。
- 收款账户绑定不写成实名认证或渠道认证。
- 相册上传后进入审核状态，不直接显示为公开成功。

## 7. 操作反馈覆盖检查

| 操作类型 | 成功反馈 | 失败反馈 | 防重复/恢复 |
| --- | --- | --- | --- |
| 登录/注册/改密 | 跳转或持续说明 | 字段+全局错误 | 提交busy；敏感字段不持久化 |
| 关注/收藏/点赞 | 图标/关系局部更新 | 局部回滚或Toast | 单项busy；账号切换取消旧请求 |
| 拉黑/清空/结束直播/删除照片 | 状态/列表更新 | 保留当前内容 | 危险确认；提交中不可重复 |
| 保存资料/直播间/介绍 | 成功Toast+最新版本 | 字段或内联错误 | 保存busy；版本冲突刷新 |
| 送礼 | 本人确认动画+余额重读 | 明确错误或待确认Notice | 原requestId恢复；不换键 |
| 申请提现 | 冻结等待审核说明 | 明确错误或待确认Notice | 二次确认；原四参数恢复 |
| 开播准备 | 展示敏感凭证 | 明确错误或恢复卡 | 原幂等Key恢复；不新建场次 |
| 相册写操作 | 最新相册与审核状态 | 冲突刷新或待确认 | 原版本/文件/照片号恢复 |
| 列表刷新/分页 | 新数据/到底 | 保留已加载项 | 请求单飞、冷却或重试 |

## 8. 跨平台覆盖检查

- H5：已覆盖320–430px、动态 viewport、安全区、浏览器地址栏、触控、滚动容器、键盘遮挡、横滑Tab、静音自动播放和网络降级。
- PC：已覆盖1024/1440宽度、多列网格/双列工作台、Hover/Focus、键盘访问、对话框/抽屉、长内容和长数字。
- Android/iOS：已给出系统安全区、原生返回、系统分享、剪贴板、日期选择器、键盘、状态栏和权限的设计差异；因无原生工程，深链、推送、相机/麦克风直播、系统支付和防截屏均标待确认。
- 可共享：业务状态机、页面信息架构、视觉Token、字段校验、金额/幂等语义。
- 需独立稿：登录键盘态、直播横竖屏/音频授权、底部高弹层、主播敏感凭证、提现确认、相册文件选择、系统分享。

结论：现有实现可以把 H5 与 PC 作为同一响应式设计系统；不能把 Android/iOS 写成“已有原生客户端”。

## 9. 发现的源码事实与设计风险

| 发现 | 风险 | 设计处理 |
| --- | --- | --- |
| 榜单使用5条本地静态数据 | AI可能误认为已上线数据能力 | C-P03标占位，所有数据口径待确认 |
| 新秀/广场未传专用筛选条件 | 入口与业务口径可能不一致 | 保留现有入口并加产品批注 |
| 直播聊天输入和“更多”被禁用 | AI可能补出IM/弹幕 | 明确只做禁用占位 |
| 实时适配器未配置 | AI可能承诺实时到账/全房广播 | 以HTTP事实为准，事件只触发重查 |
| 礼物动画是本地成功反馈 | 误解为全房广播完成 | 文案限定“已确认发送” |
| `/movies`、`/about`仅占位 | AI可能扩展电影/品牌业务 | 排除正式生成，信息待确认 |
| 调试路由有公开路径 | 生产环境暴露内部能力 | 需求写为导航/公网隔离 |
| 原生工程缺失 | 平台能力无法核实 | App只出适配规范，能力全部待确认 |
| 多处业务页硬编码中文 | 中英文设计可能不可落地 | i18n列为部分实现，不要求全量双语稿 |
| 正式主题入口不完整 | 生成深浅模式后用户无切换路径 | 支持系统跟随；手动入口待确认 |

## 10. 待确认清单

以下内容无法由源码确定，设计阶段必须由产品/业务补充，不得由 AI 自行决定：

1. 正式品牌名、Logo、中文名、品牌字体、版权与视觉资产授权。
2. 用户协议、隐私政策、客服、举报、许可证和关于页正式内容/URL。
3. 榜单接口、排名口径、刷新频率、并列规则、是否允许跳主播主页。
4. 新秀与广场的真实筛选/推荐规则。
5. 是否需要正式主题切换入口、完整英文或其他语言。
6. Android/iOS 技术容器、原生导航、深链、推送、权限、系统支付、防截屏及发布计划。
7. 直播是否支持横屏；现有源码只能证明响应式竖屏/桌面观看。
8. 主播申请标签的数据源；当前只能证明数字 ID 文本格式。
9. 支付宝/微信收款何时具备真实出款渠道；当前只能证明账户可绑定。
10. 聊天/弹幕/私信、守护购买、客户端充值等未来能力是否立项；当前均不存在。
