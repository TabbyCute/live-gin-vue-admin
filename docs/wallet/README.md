# 钱包账务交付说明

本模块落实“分析v1”最后确认的生产范围：COIN 钱包账户、余额流水、系统人工充值申请、双人审核、驳回、全额冲正、管理后台页面及 APP/H5 查询契约。消费、自动支付、冻结/解冻、转账、提现和主播结算尚未开放；没有任何直接改余额接口，也没有自动审核后门。

管理后台包含“钱包介绍”“钱包账户”“余额流水”“人工充值单”四个动态菜单，页面位于`web/src/view/wallet/`。用户列表显示完整绑定手机号、当前可用余额，并可带账号跳转到三个业务页面；钱包业务查询同时支持公开账号和完整E.164手机号。存量数据库启动时幂等补齐菜单与API元数据；权限仍由后台角色菜单/API授权控制，不以隐藏按钮代替服务端鉴权。

## 实现与不变量

沿用 Router → API → Service → Model 和 enter.go 注册。新增单数表：

| 表 | 用途与约束 |
| --- | --- |
| wallet_account | account_id + currency_code 唯一；available_balance、frozen_balance、version 非负；无软删除 |
| wallet_ledger | 只追加；ledger_no、business_type + business_no、wallet_account_id + wallet_version 分别唯一 |
| wallet_adjustment_order | 人工入账及冲正申请；created_by + request_id重试唯一、source_type + external_order_no资金凭证全局唯一；完整申请人、复核人、原因、凭证、IP、时间及关联单号 |
| wallet_daily_quota | UTC自然日账户和管理员累计入账额度；联合唯一键和行锁；冲正不返还额度 |
| wallet_audit_log | 与业务写入同一事务的只追加审计；不依赖普通HTTP操作日志成功与否 |

金额为有符号64位整数最小单位。HTTP金额、版本、管理员ID使用十进制字符串；业务时间为毫秒时间戳。COIN不代表任何法币兑换关系。frozen_balance预留且当前必须为0。查询未开户账号返回零余额，首次实际入账时原子开户并记审计，设置状态不会开户。每笔人工充值均须实际资金凭证号和凭证引用；申请人提交后由另一人核验真实到账。

入账状态：pending → credited 或 rejected。审核通过、余额更新、额度更新、流水追加、订单终态和审计在一个InnoDB事务内提交，因此不保留可能悬挂的approved中间态。普通管理员的审核者必须与申请者不同；固定顶级超级管理员`userId=1`不受钱包角色列表和自审限制，但管理员启用状态、订单状态、凭证、额度和账务校验仍会执行，创建与审核分别写入审计。

冲正：为已入账grant单创建kind=reverse申请，金额及账号继承原单。申请阶段不变余额；另一管理员审核后追加ADMIN_REVERSE负数流水，原单变成reversed，冲正单变成credited。原流水保留。仅支持全额、一次成功冲正；禁止冲正一张冲正单。待审冲正占用原单，驳回后释放，可使用新requestId重新申请。余额不足或钱包停用时拒绝执行，订单仍pending，可由审核者驳回。

数据库行锁顺序：管理员 → 原入账单 → 冲正单 → live_account（入账时）→ 钱包 → 排序后的每日额度。相同管理员创建申请会串行化以限制待审单数量；不同钱包不使用全局互斥锁。只对明确回滚的MySQL死锁1213和锁超时1205最多重试4次，带退避且响应context取消。连接中断或提交结果未知不盲目重放。

流水和审计同时有GORM钩子和数据库触发器阻止UPDATE/DELETE；订单和钱包禁止DELETE；订单创建时的账号、金额、原因、凭证、来源、请求摘要和创建元数据由数据库触发器冻结，审批时另行核对请求摘要。所有事实永久保留，普通HTTP日志清理任务不清理钱包表。特权DBA仍可改变数据库结构，所以必须结合数据库授权、变更审批和备份。

## 幂等和失败处理

- 创建和冲正申请使用`requestId`，同一管理员跨两种申请共享命名空间。相同键和规范化后的相同请求返回原单；更换账号、金额、原因、凭证或操作类型返回47005。
- 真实资金以`sourceType + externalOrderNo`全局防重，不依赖管理员、目标用户或金额；人工凭证号统一大写ASCII。驳回和冲正不释放凭证键，跨实例竞争由数据库唯一索引裁决。
- 审核使用订单状态和行锁幂等。相同审核者、决定、原因重试时会复核已提交流水和事务审计，再返回原结果；另一审核者或冲突决定返回47005。损坏或缺失的提交事实返回47011，不会重新记账或返回虚假成功。重复调用不会重复写审计或流水。
- 断网、超时或47012时，客户端保留原requestId/原审核参数，查询单据或重试原请求；不能生成新key当作重试。
- 每次余额变动先核对尾流水版本与余额，开户/充值另核对内部账号ID与公开账号一致，发现旁路改账立即停止；查询对账进一步检查完整连续链、订单↔流水及事务审计对应关系。详情与对账使用每批只读快照，不持资金行锁。
- 钱包状态停用只阻止资金变化，保留查询；停用/启用有事务审计。目标用户禁用、封禁、注销或软删除时禁止新入账；已发生账务的冲正不依赖用户可登录状态。

## 权限与扩展

默认读、申请、审核角色均为888；普通管理员必须由两个不同账号操作，固定顶级超级管理员`userId=1`例外。ID 1拥有全部钱包管理权限，不受read/create/review角色列表限制，但仍会核验管理员记录存在且启用。其他管理员可分别配置角色列表，实现财务申请/复核分工。每个服务入口除JWT外再次读取管理员当前启用状态和角色归属；不能依赖菜单隐藏或令牌内过期的角色信息。读权限包含申请/审核角色。

APP只接受独立Bearer token，从JWT取本人账号，不接受accountId/accountNo选人；返回专用DTO，隐藏管理员、内部原因和凭证。管理接口要求后台x-token；服务内部不得接收Gin上下文。

未来新增业务时，应明确金额语义、币种、负数规则、余额分配、审核/支付订单及幂等键，再扩展`service/wallet/posting.go`中的内部`postLedger`事务记账路径；该方法没有HTTP入口，不独立提交事务。不要把支付回调或消费模块接到钱包表UPDATE，也人工接口不能用于支付宝/微信回调；必须先校验第三方真实支付事实。新增消费后需要同步扩展冲正资金不足政策、对账业务类型和冻结不变量；当前接口没有预留任意扣款入口。
