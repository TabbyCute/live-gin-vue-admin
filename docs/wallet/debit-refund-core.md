# 扣款与消费退款内核接入

更新：2026-10-30。入口位于 `server/service/wallet/transaction.go`。本轮只实现账务内核、查询溯源和校验；商品、定价、订单履约、等级、主播收入、奖励、支付渠道等尚未实现。

## 调用边界

| 方法 | 事务归属 | 适用情况 |
| --- | --- | --- |
| `Debit(ctx, input)` | 内核开启并提交事务 | 上游已有可靠业务状态管理的内部作业 |
| `Refund(ctx, input)` | 内核开启并提交事务 | 上游已有可靠退款单状态管理的内部作业 |
| `DebitInTx(tx, input)` | 调用者持有的真实事务 | 业务订单、钱包和履约数据在同库原子提交 |
| `RefundInTx(tx, input)` | 调用者持有的真实事务 | 业务退款单、撤销权益和钱包在同库原子提交 |

没有对应的 APP/H5 或后台任意扣款/退款 HTTP 接口，直接请求会得到404。`MovementInput`不能绑定HTTP请求体。未来业务接口必须自行验证用户身份、订单归属、价格、数量、业务状态、退款政策、请求限流和权限，再构造内部参数。尤其不能采用前端传入的金额、收款人、操作者身份或“已支付”标志。

内核信任进程内调用方的业务授权。`ActorType=admin/system`不是可以绕过授权的客户端字段；业务服务须验证实际后台权限或内部任务身份。用户类型的ActorID额外强制与AccountID相同。`userId=1`的后台最高权限不允许负余额、超额退款或绕过账务完整性检查。

## 参数

| 字段 | 约束与来源 |
| --- | --- |
| AccountID | 稳定的内部用户ID，来自认证身份和已核实订单，不是手机号 |
| CurrencyCode | 当前仅COIN，空值按COIN处理 |
| Amount | `1`至`9223372036854775807`的正整数字符串；扣款、退款均传正数，不接受小数、空格、前导零或JSON数字 |
| BusinessType | 固定业务命名空间，`[a-z][a-z0-9_]{0,31}`，例如未来的`gift`或`vip`；不能由用户任意选择 |
| BusinessNo | 持久化业务订单号/业务退款单号，1—128位ASCII，首位字母数字，后续可含`_.:/-`，区分大小写 |
| OriginalNo | 扣款必须为空；退款必填原扣款的`wt_...`账务交易号，不是充值单号或流水号 |
| ActorType / ActorID | `user`+规范十进制用户ID、`admin`+规范十进制管理员ID、`system`+任务服务标识（与BusinessType同格式） |
| ActorIP | 服务端取得的合法IPv4/IPv6；后台任务可使用自身地址/回环地址，不伪造用户IP；不盲信转发头 |
| TraceID | 服务端追踪号，1—64字符，无控制字符和首尾空白；不得包含令牌或密码 |
| Reason | 内部记账原因，3—500字符，无控制字符和首尾空白；只供授权后台读取 |

结果包含`TransactionNo / LedgerNo / Amount / BalanceAfter / WalletVersion`，金额和版本是字符串。`BalanceAfter`是这笔记账发生后的余额，**重试返回的仍是原结果，不是当前余额**；需要当前值时重新查Balance。InTx结果只在外层Commit确认成功后有效。

## 幂等与原子性

永久唯一键为`(kind, business_type, business_no)`，不包含用户、管理员或实例。原参数重试返回原交易，并检查原交易、流水、审计和退款累计额；更改金额、账号、币种、原扣款、业务、操作者或原因会返回ErrConflict。IP和TraceID可以在重试时变化，但只保存第一次成功的值。

同一业务退款操作永久使用同一业务退款单号；下一次部分退款才使用新的退款单号。消费原单和退款单必须属于同一用户、币种和BusinessType。禁止退充值单、退另一用户、退另一退款、累计超过原消费金额。已经全退的原单也不释放幂等键。

锁顺序为用户共享锁→钱包排他锁→本钱包交易。一个钱包的写入由行锁串行，跨钱包不使用全局应用锁；交易唯一索引处理跨账户误用同一业务键。金额计算、钱包版本CAS、尾流水校验、退款总额校验、数据库CHECK及不可变触发器提供多层检查。

外层事务推荐READ COMMITTED；内核也支持已建立旧快照的REPEATABLE READ事务，记账读取使用当前读，避免新余额与旧幂等/退款数据混用。只读溯源和对账仍使用RR快照，不持资金行锁。业务方也应对自己的订单采用正确行锁/条件更新。单个业务事务优先只处理一个钱包；未来涉及多个钱包时需单独设计固定锁顺序，不要自行把它当作转账内核。

消费订单接入框架（示意，业务方法尚未实现）：

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    // 1. 锁定业务订单，验证当前认证用户、服务器价格、状态和幂等内容。
    // 2. 若订单已经完成，校验/返回原业务结果，不重复发权益。
    receipt, err := walletService.DebitInTx(tx, trustedInput)
    if err != nil { return err } // 必须回滚整个事务，不能吞掉错误继续提交。
    // 3. 将receipt.TransactionNo和receipt.LedgerNo写到业务订单。
    // 4. 同事务更新本地权益/库存/订单终态（或写事务发件箱）。
    return finalizeBusinessOrder(tx, receipt)
}, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
// 仅在err==nil且Commit成功后向用户报告业务成功。
```

InTx不提交、不自动重试；任何错误必须回滚外层事务。不能先独立调用Debit扣钱，再用另一事务完成业务订单并认为两者原子。不得在持有资金行锁时发网络请求。跨库/跨服务履约需要单独设计事务发件箱、幂等消费者及补偿状态机，本轮未实现。

独立Debit/Refund只对数据库明确回滚的1213/1205最多执行4次事务尝试，支持context取消；其他连接错误和Commit结果不明不自动重放。调用方应设置截止时间。提交响应丢失时用原业务单、原参数查询/重试，不生成新单号；外层业务事务重试必须覆盖整个订单操作，不能只重试钱包SQL。

## 状态和边界

- 未开户扣款拒绝，不会隐式建钱包。没有原扣款不可能合法退款。
- 新扣款要求用户正常且未软删除；注销/封禁用户允许退回其原消费款。停用钱包阻止新扣款和新退款。已成功交易仍能按原参数查询式重试，停用不会抹掉事实。
- 不支持透支、冻结余额消费、转账和多币种；`frozen_balance`仍要求0。
- 余额达到int64上限后退款拒绝，整个事务回滚；钱包版本达到上限也拒绝，禁止整数环绕。
- 一笔原消费最多1000笔成功退款（包含全额退款），超过数量返回ErrLimit；原成功退款的重试仍可返回。该上限限制查询资源，业务应合并退款计划，不能通过改原单规避。
- 消费退款只把COIN退回原钱包，不是支付宝/微信/银行卡现金退款。人工充值冲正仍是独立双人复核流程，若充值已经消费导致余额不足，不能强制扣成负数。
- 退款不返还人工充值日额度。奖励入账需要未来独立奖励业务；不能虚构消费原单发奖励。

主要错误：ErrInvalid(47001)、ErrAccount(47003)、ErrNotFound(47004)、ErrConflict(47005)、ErrLimit(47007)、ErrDisabled(47009)、ErrInsufficient(47010)、ErrInvariant(47011)、ErrRefundLimit(47016)。内部方法返回可通过errors.Is识别的错误；未来HTTP业务层必须映射安全错误，不能暴露SQL、DSN或堆栈。

## 后台追踪与核查

钱包管理→余额流水，按公开账号或完整手机号找到用户，点击任意一行的“交易详情”。也可在“交易溯源”输入`wl_`流水号、`wt_`账务交易号、`wa_`人工充值单号，或者用完整业务命名空间+业务单号+动作查询。

页面展示发生金额、前后余额、连续版本、原消费、累计退款和每笔退款、业务来源、操作者、IP、TraceID、原因及事务审计。退款记录每页50笔，有下一页时继续加载；后台管理员展示昵称和ID，用户和系统任务采用各自身份标识。用户/任务记账的ledger.operator_id为0，不代表管理员0；应以关联交易的actorType/actorID为准。

接口为`GET /api/v1/admin/wallet/transaction/trace`，详见api.md。APP token和无读权限的管理员不可访问。发现完整性异常时详情仍展示现存记录并返回issues警示，不能把这种结果当作完整性通过。完整核查使用account/check，必须推进流水、人工单、消费交易三个游标直到hasMore=false。

消费和退款每次成功只产生一条交易、一条不可变流水、一条事务审计，并与余额变化原子提交；退款还更新原扣款累计额。失败尝试不产生余额变动，按上层业务日志记录。后台可查全部已提交的资金变动，但高权限DBA破坏保护或删除备份不在应用防篡改能力之内，仍需最小权限、数据库备份和恢复演练。
