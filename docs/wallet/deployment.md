# 钱包部署与运维

## 发布前与数据库

生产支持MySQL 8.x（8.0.16及以上），InnoDB、utf8mb4_bin（字节敏感幂等键）、事务和CHECK约束必须实际启用；SQLite只用于开发测试。当前未验证PostgreSQL、MariaDB、TiDB等兼容数据库，初始化会拒绝其他dialect、MariaDB版本、低于基线的MySQL和非严格SQL模式。启动同时核对实际列的类型、长度、有符号性、NULL、默认值、列排序规则及自增属性，主键/索引列顺序、前缀及可见性、CHECK实际执行状态及表达式、触发器定义。应使用现有主库处理钱包读写，不能将审核或即时余额查询路由到有延迟的只读副本。

推荐先在预发库备份并执行迁移，再发布服务。钱包新部署没有历史余额导入，不修改live_account表，也不读取项目配置连接业务库进行测试。

```sh
cd server
# 通过部署平台向进程注入WALLET_MIGRATION_DSN，禁止把真实密码放进仓库。
go run ./cmd/wallet-migrate
# 只读校验，可重复执行；缺表/列/索引/约束/触发器时非零退出。
go run ./cmd/wallet-migrate -verify
```

示例DSN格式：`user:password@tcp(host:3306)/database?parseTime=true&timeout=5s`。完整迁移命令只处理钱包六张表及触发器。MySQL DDL不能整体事务回滚：失败时停止发布，修复权限/结构后重跑；不应删除已写入的账务表重新建库。

### 2026-10-30消费内核升级

本轮现有五张表字段、索引和约束不变，只新增`wallet_transaction`及其两个保护触发器。已具备完整人工充值结构的数据库可执行`go run ./cmd/wallet-migrate -transactions-only`，随后`-verify`。该命令只创建缺失的新表及新触发器，然后严格验证全部六张表；不ALTER旧表、不填充历史数据、不创建临时修补列/索引，也不自动修正已存在的错误新表。升级不要求删除任何旧账务表。

新应用启动会幂等补齐“交易溯源”菜单和GET API元数据；新菜单默认赋予888，其他角色按权限管理授权。开始消费写入前应完成所有钱包读端/后台更新，旧版本的对账不认识消费类型，不能新旧混用做财务判断。回退时保留新表与事实，并暂停消费业务入口。

已有统一AutoMigrate流程也已接入钱包：未关闭自动迁移时启动创建表、索引和保护触发器；关闭自动迁移时仍会同步API元数据并严格校验钱包结构。钱包DDL和菜单同步使用按数据库隔离的MySQL命名锁，在同一专用连接获取、执行和释放；获取等待最多30秒，整个操作最多5分钟，失败后可重试，不新增锁表。连接取消或释放失败时会淘汰可能仍持锁的连接。多实例发布仍推荐由一个迁移作业先完成DDL，应用设`system.disable-auto-migrate: true`；该命名锁不替代项目其他模块的发布协调。钱包配置冻结为启动快照，改变角色或额度需让所有实例使用同一配置并重启。

MySQL完整结构核验固定使用6次批量SELECT，包含运行环境、表、列、索引、CHECK及触发器；60秒总上限同时尊重调用者更短的截止时间。超时、权限和连接错误原样返回，不会误报成缺少约束。检查失败仍禁止启用钱包，不会自动放宽约束。

## 数据库授权

迁移账号需要钱包表DDL、索引及TRIGGER权限。运行账号最低账务权限建议：

| 对象 | 运行时权限 |
| --- | --- |
| wallet_account | SELECT、INSERT、UPDATE，不授DELETE |
| wallet_adjustment_order | SELECT、INSERT、UPDATE，不授DELETE |
| wallet_daily_quota | SELECT、INSERT、UPDATE |
| wallet_transaction | SELECT、INSERT，UPDATE仅refunded_amount列；不授DELETE及核心列UPDATE |
| wallet_ledger、wallet_audit_log | SELECT、INSERT，不授UPDATE/DELETE |
| live_account、sys_users、sys_user_authority | 钱包读取；应用其他模块的写权限按既有职责配置 |
| sys_apis、sys_operation_records | 按项目启动元数据同步及操作日志所需授权 |

MySQL启动校验读取information_schema.TRIGGERS，需要对相应钱包表有TRIGGER元数据可见权限。TRIGGER权限本身允许变更触发器，因此必须同时限制运行账号的UPDATE/DELETE/DDL权限，不能仅依靠触发器保护。不要把全库ALL PRIVILEGES授给生产应用账号；普通开发库的root配置不应直接用于生产。

保持严格SQL模式。生产持久性建议`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`并验证备份/PITR、主从切换和故障恢复。没有在真实生产拓扑中测试断电、主从故障转移或跨地域容灾，本地功能测试不能替代这些验收。

## 业务配置与上线验收

将wallet.example.yaml合入当前指定配置。默认单笔1,000,000 COIN、账户UTC日10,000,000 COIN、申请人和审核人各UTC日10,000,000 COIN；所有人工充值均须资金凭证号及凭证引用；evidence-threshold仅保留兼容旧配置，不再放宽小额凭证要求；每个申请人最多100张pending单。零值采用默认，负数或日额度小于单笔上限会拒绝启动。冲正不占新增充值额度，也不返还已用额度。普通管理员应至少准备两个不同账号；固定顶级超级管理员`userId=1`拥有全部钱包管理权限且可自审，应限制账号使用并重点监控其创建、审核和登录审计。

1. 确认两个独立APP和ADMIN JWT密钥、后台访问范围、当前角色及钱包角色配置；凭证必须存储在受控文件系统中。
2. 创建小额测试申请，确认pending且余额不变；本人审核返回47006，另一管理员审核后恰好一条流水。
3. 原样重试创建和审核，确认余额不重复；更换金额复用requestId返回47005。
4. 创建并双人审核冲正，原单reversed、冲正单credited，新增负数流水且原流水保留。
5. APP只能查本人，其他账号参数被拒绝；普通后台角色无权操作。
6. 完整跑三条游标的对账，从0开始直到hasMore=false，累计issues必须为空；外部调度同步新增afterTransactionId。
7. 消费业务接入后，在隔离验收账号验证同事务扣款/履约失败回滚、部分退款/超退拒绝和后台完整溯源；不要用普通HTTP开放任意金额记账。

## 监控与异常处理

使用现有访问日志/指标系统监控47007额度拒绝、47010余额不足、47011不变量异常、47012数据库失败、47013资金防重拒绝、47015历史单拒绝、47016超额退款、接口延迟、数据库连接池等待、死锁重试日志、pending订单积压。HTTP的47011会记录`wallet invariant violated`错误日志，对账不一致会记录`wallet reconciliation inconsistent`错误日志；可按消息和结构化字段配置告警。内部Debit/Refund/InTx调用者须记录错误、业务单号和TraceID，不能丢弃错误或把普通重试作为新业务。普通操作日志中的资金凭证号、凭证引用和请求摘要脱敏，业务单和事务审计仍保存核查事实。当前没有接入外部告警渠道或自动发送通知。

- 47011：停用相关钱包，保存当前订单、流水及审计，执行分批对账和数据库排查；不要执行SQL改余额“修复”。
- 提交结果未知：保持原requestId或审核参数，通过查询原单及重试确认，禁止另发新订单。
- 长时间pending：业务人员按申请和凭证审核或驳回；没有“自动补发pending单”的任务。
- 错账：走冲正申请和复核。当前版本没有部分冲正、强制负余额或反向删除流程。
- 凭证：仅保存引用，不抓取URL；由授权复核人员检查真实内容和访问权限。不能把引用存在等同于已经验证凭证真实性。

应由已有运维调度系统定期调用account/check，对业务账号从0开始扫描，保留每批结果并在issues非空时报警。它只读，不自动修账；没有私自配置定时任务。每批使用REPEATABLE READ只读事务取得同一个MVCC快照，不持钱包/订单行锁，不阻塞充值审核。默认100条、最多1000条，生产按实际负载调节批大小和频率。批次之间可以有新提交，整体扫描不是跨所有请求固定的全库快照。核验包括订单与流水、余额连续链、创建及审核审计，以及消费/退款交易、原单和累计退款的对应关系。三个游标为afterVersion、afterOrderId、afterTransactionId，必须同时推进。

回滚应用时保留所有钱包表、触发器及历史；旧版本不认识钱包接口时在网关暂停入口。恢复到新版本后先校验结构和对账，不能回退到旧数据库快照后继续接受已处理过的业务请求。

## 已有旧版钱包的升级（必须停写）

1. 暂停全部钱包写入口，停止旧版本实例；备份钱包五张表和触发器，并先在备份恢复库演练升级。不要在新旧代码混跑期间迁移：旧代码没有凭证号，必须禁止其继续申请。
2. 用单独迁移作业执行wallet-migrate。升级先补source_type/external_order_no列，再将历史grant标为legacy、external_order_no填原内部单号；历史reverse标为reversal并保留原申请摘要。然后创建联合唯一索引、约束和不可变触发器；重复执行不改已迁移事实。DDL非整体事务，任何失败均保持停写，修复后重跑。
3. 历史余额和流水完全保留。legacy待审grant不能审批（47015），核查后驳回；对账会对未驳回legacy记录报告legacy_source_unverified，以提示尚未核验历史资金来源；既有已入账grant仍可按双人工作流冲正。禁止用SQL给旧单补造凭证再审核，不可变触发器会拒绝。
4. **历史已入账单缺少真实资金号，代码无法推断它是否对应将要提交的某笔资金。**启用新人工充值前必须人工核对历史资金、确定切换时点和新凭证受理范围，确保历史到账资金不再通过新入口提交；大量存量真实充值需要专门的、审计完整的真实凭证映射迁移方案。legacy内部单号不是跨历史资金的自动去重保证。
5. 运行wallet-migrate -verify，校验主库结构；部署全部新实例，确保DSN所有连接使用同一严格sql_mode，禁止运行中改成宽松模式。先执行小额双人充值、跨管理员重复凭证、冲正和完整对账验收，再恢复入口。

每笔人工充值仍必须由审核人核验实际银行/收款渠道到账。凭证号去重不能识别伪造凭证、同一资金使用两个不同编号或错误兑换率。当前充值金额是COIN整数，不定义法币兑换规则；自动支付宝/微信支付须另建支付订单，以渠道及第三方交易号全局防重、核验签名/商户/币种/金额后，在同一事务内调用内部postLedger，不能调用人工充值API冒充支付完成。


## 2026-10-30入口保护与容量预算

默认单进程APP钱包在途64个、后台钱包在途16个，两个入口独立；`wallet.app-max-inflight`和`wallet.admin-max-inflight`可配置1—4096，0使用默认，负数或超过4096拒绝初始化。路由初始化时固定，无本地等待队列，无按攻击者IP增长的内存表，不引入Redis作为记账正确性的依赖。容量已满立即返回HTTP503/47012及Retry-After: 1，客户端应随机退避，并保留原写入编号及参数。限制是每实例的在途请求数，不是全局QPS限制；多实例总量和数据库其他模块的连接需求须一起预算。调高数字不会提高单个钱包串行资金写入的能力。

钱包上下文预算8秒，APP包含JWT查库；后台继承的JWT中间件位于钱包group之外，因此全链路网关仍需独立设置超时。正文读取由底层HTTP read deadline限制，不只依赖context；早期拒绝HTTP/1请求关闭连接，避免清理未读正文时长时间阻塞。所有响应禁止缓存。内部业务服务调用Debit/Refund/InTx不经过HTTP guard，上游必须传有界context，并控制并发。

网关部署须限制总连接数、请求头读取时间、请求头/body大小、IP/已认证主体的速率和整体突发；后台限制来源与授权范围。应用内在途保护不能替代跨实例公平限流、DDoS防护或TLS配置。上述网关策略本轮未对实际环境部署或验收，不能视为已经生效。

通用HTTP操作日志最多再等待2秒，客户端断开后仍尽力写入；其失败不改变已提交的资金结果。财务流水和wallet_audit_log仍与资金写入同事务，审计失败整笔回滚。操作日志JSON无法安全解析或脱敏结果超限时隐藏整段，避免回退到原始凭证；API依赖错误仅记录分类和MySQL错误编号，不记录原始SQL/凭证文本。

管理端现使用固定Axios版本并纳入pnpm锁文件，安装使用`pnpm install --frozen-lockfile`。本轮前端生产依赖扫描仍有11项公共依赖告警，详见封版报告；这些需要单独处理或证明不可达，不能把钱包回归通过解读为整个平台供应链零风险。
