# 钱包生产复核与优化（2026-10-29）

本次复核针对当前会话交付的钱包账户、余额流水、系统人工充值、后台操作及初始化代码。已修复发现的应用层问题，并对隔离 MySQL 实际执行并发、事务、结构破坏和失败恢复测试。此记录不代表整个平台或生产基础设施已经完成高可用认证。

## 本轮修复

| 问题与影响 | 实现与验证 |
| --- | --- |
| 新建充值可能沿用旧列表第一行的账号，输入的新手机号没有重新定位 | 按当前账号、手机号重新调用后台定位，两者冲突则拒绝。输入变化或请求过期后丢弃旧响应。测试覆盖旧列表与新手机号不属于同一用户的情况。 |
| 查询乱序、切换用户、页面缓存以及确认弹窗期间编辑字段可能混用上下文 | 查询使用请求序号，流水分页绑定已经提交的查询条件；审核、创建、冲正和钱包状态操作固定提交参数，阻止重复提交。离开页面使旧响应失效。用户列表从钱包返回时刷新余额。失败创建保留原请求编号和表单，避免换编号重试。 |
| 详情和对账通过共享行锁读数据，容易阻塞同钱包的充值或审核 | 改为每批 `REPEATABLE READ` 只读事务快照。真实 MySQL 测试暂停读取，验证首次开户、已有钱包充值、订单审核均能继续提交，且旧快照内部一致。分页之间是不同快照，不是一次跨所有页的冻结。 |
| 多个实例同时初始化钱包可能争抢迁移和菜单同步 | 使用按数据库区分的 MySQL 命名锁，同一专用连接获取、执行及释放，未增加锁表。独立会话避免 GORM 语句状态污染。覆盖 8 路并发迁移、失败后释放锁以及取消传播。此锁只保护钱包初始化；平台其他模块仍应采用独立迁移作业。 |
| 启动验证数据库结构需要较多远端往返，数据库错误可能被误报为缺少约束 | 运行环境加五类元数据共 6 次批量查询，保留真实错误及调用方取消。继续严格核验类型、长度、NULL、默认值、引擎、排序规则、主键、索引、CHECK 和触发器定义。新增索引列顺序、前缀、不可见索引、复合主键破坏测试。 |
| 审核重试仅凭订单终态返回成功，不能发现缺失或被错误修改的提交事实 | 重试成功前核验创建/审核审计及原始流水；开户时核对内部账号 ID 与公开账号。对账按批核验订单对应审计，新增 `order_audit:<orderNo>` 问题码。篡改、遗漏或重复记录返回资金完整性错误，不补记、不重复入账。 |
| 财务响应和通用操作日志仍有隐私与告警缺口 | 钱包响应增加 `Cache-Control: no-store`；HTTP 操作日志遮蔽凭证引用、资金凭证号、请求摘要。完整性错误和对账不一致输出可被日志平台采集的结构化错误日志，不记录请求凭证正文。 |

以上变更保留 `userId=1` 的钱包最高管理权限和自审能力；金额边界、账号状态、订单状态、额度、凭证防重以及资金完整性检查仍然执行。

## 数据库处理

**本轮没有表结构变更，没有对远端执行 DROP、ALTER、INSERT、UPDATE 或 DELETE。** 当前结构能够支持这些改进，不需要通过删表重建来清理数据，也没有增加兼容字段、补丁索引或迁移锁表。

使用现有生产配置的连接信息执行了远端只读结构校验和元数据检查，未在文档或命令输出中记录密码：

- `wallet-migrate -verify` 通过；MySQL 版本为 `8.0.46-0ubuntu0.24.04.4`。
- 5 张钱包表的索引数（包含主键）依次为：账户 2、流水 4、充值单 8、额度 2、审计 2，与当前模型一致；8 个 CHECK、7 个保护触发器通过校验。
- `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、`log_bin=1`，符合当前持久性基线。
- 远端验证命令一次观察耗时约 9.17 秒，包含 `go run` 编译与网络时间，仅作为启动验证记录，不作为吞吐或延迟指标。

## 验证证据

复现命令、历史测试及本轮新增场景见 [testing.md](testing.md)。本轮确认：

- 注入本机隔离 MySQL DSN 的全仓 `go test ./... -count=1` 通过，钱包 MySQL 场景实际执行。
- `go vet ./...`、`go build ./...` 通过。
- 钱包 Service/API/Router、initialize、middleware 的 `-race` 通过，包含真实 MySQL 并发和失败路径。
- `npm run test:wallet` 的 10 个实际 Vue 组件逻辑回归通过，`npm run build` 通过。这些是组件逻辑测试，不是完整浏览器交互自动化。
- 既有跨管理员凭证防重、审核与驳回竞争、首次开户、冲正、额度、锁超时、未知提交结果及回滚场景继续通过。

测试使用本机 `127.0.0.1:13326` 的独立 MySQL 容器，每个场景创建随机测试库，禁止使用生产业务库。前端构建仍有项目已有的大于 500 kB 的资源分块提示；未为了消除提示调整无关业务打包。

## 上线仍需完成的部署验收

代码和本机测试不能证明主从切换、物理掉电或备份恢复满足业务目标，以下事项仍需在实际部署拓扑完成：

1. **数据库权限隔离。** 当前检查使用现有配置中的管理账号。正式运行应使用独立的最小权限应用账号，迁移账号与运行账号分离；应用账号不能直接删除账务或变更保护触发器。按 [deployment.md](deployment.md) 配置所需权限并进行一次完整业务验收。
2. **数据库高可用和恢复。** 明确 RPO/RTO、复制及故障切换策略；实际演练主库断连、切换、备份恢复、时间点恢复，随后核对订单、流水、余额与审计。刷盘参数正确不能替代这些演练。
3. **多实例配置一致与可观测性。** 所有实例使用一致的币种、额度和权限配置；采集 `wallet invariant violated`、`wallet reconciliation inconsistent`、锁等待、数据库错误和请求延迟，接入明确的告警处理流程。本次新增日志，没有代替部署侧配置告警平台。
4. **目标容量验收。** 使用真实硬件、预计流水规模和热点账号分布评估充值、对账及审核延迟，确认数据库连接池、网关超时和备份窗口。相同管理员、同一钱包或日额度的写入竞争需要串行，不能以本机短测推导生产容量上限。
5. **实际资金核验。** 人工充值仍要求管理员验证到账凭证。接口能够阻止相同规范化凭证重复记账，无法自动证明不同凭证号对应的资金是否真实、是否为同一笔资金。自动支付必须另建支付订单并验签后调用内部记账路径。

部署、客户端接入及资金异常处理分别见 [deployment.md](deployment.md)、[frontend-client-integration.md](frontend-client-integration.md) 和 [api.md](api.md)。
