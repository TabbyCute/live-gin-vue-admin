# 七、POST /app/live/anchor/apply

用途：

> 普通用户申请成为主播；被拒绝后可以重新申请。

必须从 JWT 获取 user_id。

## 需要处理以下情况

### 1. 从未申请

如果没有 LiveAnchor：

创建主播。

初始化：

```text
ApplyStatus = 1
ApplyAt = now milliseconds

Status = 1

LivePermission = 0
PkPermission = 0
WithdrawPermission = 0

RecommendPermission 按 Model 默认值

CertStatus = 0
RiskLevel = 0
```

AnchorNo 必须使用项目统一生成规则。

必须保证：

```text
user_id UNIQUE
anchor_no UNIQUE
```

---

### 2. 已经审核中

```text
ApplyStatus == 1
```

禁止重复申请。

返回明确业务错误：

```text
主播申请正在审核中
```

---

### 3. 已经通过

```text
ApplyStatus == 2
```

禁止重新申请。

返回：

```text
已经是主播
```

---

### 4. 已被拒绝

```text
ApplyStatus == 3
```

允许重新申请。

重新申请时：

```text
ApplyStatus = 1
ApplyAt = now
AuditAt = 0
AuditUserId = 0
RejectReason = ""
```

根据请求更新允许重新提交的主播资料。

不要创建第二条 LiveAnchor。

---

### 5. 并发问题

同一个 user_id 同时请求 apply：

数据库：

```text
UNIQUE(user_id)
```

必须作为最后保护。

Service 层也先判断。

如果产生 duplicate key，需要转换为业务错误，而不是把 MySQL 原始错误返回客户端。

# 十一、GET /app/live/anchor/live/check

用途：

> 检查当前登录主播目前是否具备“开始一场直播”的业务资格。

不是简单返回：

```text

```

必须综合判断。

建议 Service：

```go
CheckLivePermission(userId uint64)
```

基本流程：

```text
查主播
↓
主播存在？
↓
申请审核通过？
↓
主播账号状态正常？
↓
封禁状态是否有效？
↓
风险等级是否允许？
↓
直播权限是否开启？
↓
认证是否满足当前系统要求？
↓
ALLOW
```

# 二十五、JWT 设计

请先检查当前项目 JWT claims。

如果要增加主播相关 Claims，不要盲目把整套主播状态塞进 Token。

推荐最多增加：

```go
IsAnchor bool   `json:"isAnchor"`
AnchorId uint   `json:"anchorId"`
AnchorNo string `json:"anchorNo,omitempty"`
```

具体 ID 类型和项目保持一致。

---

## 不建议放 JWT

不要将以下数据作为授权依据长期放在 token 中：

```text
Status
RiskLevel

LivePermission
PkPermission
RecommendPermission
WithdrawPermission

ApplyStatus
CertStatus

AgencyId
IsSigned
```

因为后台修改后：

```text
JWT 仍然是旧值
```

会导致：

> 后台已经封禁主播，但是主播旧 Token 仍显示允许直播。

这是严重问题。

---

## JWT 应该怎么用

JWT：

```text
证明“你是谁”
```

例如：

```text
UserId
AnchorId
IsAnchor
```

实时业务权限：

```text
数据库 / Redis
```

决定。

特别是：

```text
/live/check
/pk/check
```

必须实时查询主播状态。

不能只看 JWT。

---

## JWT 主播身份缓存问题

如果用户登录时：

```text
IsAnchor = false
```

后来申请审核通过：

旧 Token 仍然：

```text
IsAnchor = false
```

因此：

**任何关键主播 API 都不能因为 JWT IsAnchor=false 就永久拒绝。**

可以使用两种方式。

### 方案 A，推荐第一版

JWT 仍只存 UserId。

主播身份实时：

```text
userId -> LiveAnchor
```

查询。

这是最简单、最安全的。

### 方案 B

JWT 增加：

```text
AnchorId
IsAnchor
```

但它只能当性能优化/快速展示。

主播状态变化后：

* 刷新 Token
* 或重新登录
* 或后台有 token version

第一版没有必要复杂化。

所以本模块实现时：

**优先保持现有 JWT 不变。**

除非当前项目架构明确需要 AnchorId Claim。

# 最重要的原则

开始编码前：

**先扫描当前项目。**

特别是先寻找已有类似模块，例如：

```text
用户管理
代理管理
公会管理
文章管理
后台审核
状态修改
权限修改
```

优先模仿当前项目中质量最高、结构最接近的现有模块。

最终代码应该让人看起来像：

> 这是这个项目原本就有的代码。

而不是：

> 这是另外一个人按照另一种架构新写进去的模块。
