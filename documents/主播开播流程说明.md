# 主播开播流程与接口说明

本文说明主播从“准备开播”到“直播结束”的完整流程，包括房间与场次状态、调用接口、鉴权方式、SRS 回调、断流重连、最终结算和常见问题。

相关资料：

- [主播身份说明.md](./主播身份说明.md)：主播申请、审核、权限、封禁和账号状态；
- [直播间说明.md](./直播间说明.md)：`live_room`、`live_session` 表结构及全部字段来源；
- [html-4主播开播.html](../test/live/html-4主播开播.html)：本地接口联调页面。

## 一、核心状态

房间状态和场次状态是两套枚举，数值不能直接比较：

| 业务阶段 | `live_room.live_status` | `live_session.status` | 说明 |
|---|---:|---:|---|
| 未开播 | `0` | 无活动场次 | 房间存在，但当前没有准备中、直播中或结束中的场次 |
| 准备中 | `1` | `0` | 已创建场次和推流凭证，尚未收到有效推流 |
| 直播中 | `2` | `1` | 已收到有效 `on_publish`，或者正在短暂断流重连窗口内 |
| 结束中 | `3` | `2` | 已请求结束，正在等待资源清理和最终结算 |
| 已结束 | `0` | `3` | 场次完成结算，房间恢复未开播 |
| 已取消 | `0` | `4` | 准备后没有真正开播就被取消 |
| 失败 | `0` | `5` | 场次因系统或业务异常进入失败终态 |

完整流程：

```text
检查开播资格
  ↓
准备开播
  ├─ live_room.live_status = 1
  └─ live_session.status = 0
  ├─ 截止前有效 on_publish → 进入直播中
  └─ 准备超时 → Cancelled，房间恢复未开播
  ↓
直播中
  ├─ 统计服务更新观看、点赞和礼物汇总
  ├─ 短暂断流 → 等待重连 → 继续原场次
  └─ 主播下播 / 管理员强制结束 / 断流超时
  ↓
结束中
  ├─ live_room.live_status = 3
  └─ live_session.status = 2
  ↓
后台任务最终结算
  ├─ live_room.live_status = 0
  ├─ live_session.status = 3
  └─ live_room.last_session_id 指向本场
```

## 二、接口鉴权分类

| 标识 | 鉴权方式 | 使用方 |
|---|---|---|
| 主播鉴权 | `Authorization: Bearer <APP Token>` | 主播本人操作直播间和场次 |
| 不鉴权 | 无 | 观众查询公开直播间和公开直播列表 |
| SRS/统计回调 | 部署层真实来源 IP/CIDR 白名单 | SRS 或可信统计服务 |
| 后台鉴权 | 管理后台 JWT | 管理员强制结束场次等后台操作 |

Hook 路由本身不使用 APP 或后台 JWT，也不再要求额外 Header Token；部署时必须在防火墙、负载均衡或反向代理最外层限制真实来源 IP，不能信任客户端可伪造的 `X-Forwarded-For`。

### 服务端 SRS 配置

开发、正式和 Docker 环境配置文件都把 SRS 参数放在 `live.srs` 子配置组中：

```yaml
live:
  reconnect-window-seconds: 20
  prepare-timeout-seconds: 120
  push-token-seconds: 86400
  publish-token-key: "请替换为足够长的随机密钥"
  srs:
    app: "live"
    http_apis: "http://127.0.0.1:1985"
    push-base-url: "rtmp://srs.example.com/live"
    play-base-url: "https://srs.example.com/live"
```

| 配置 | 作用 |
|---|---|
| `live.publish-token-key` | 仅保存在 Go 服务中，用 SHA-256 派生 AES-256 密钥加密和解密 pt；不配置到 SRS 或客户端 |
| `live.srs.app` | SRS 流应用名，例如 `live`；会写入 pt 载荷并参与推流、播放 URL 拼接 |
| `live.srs.http_apis` | SRS HTTP API 基础地址，例如 `http://127.0.0.1:1985`；供后续查询流状态或主动断流等服务端能力使用 |
| `live.srs.push-base-url` | 推流基础地址；其域名写入 pt 的 `vhost`，并和 `app`、`streamName`、`pt` 拼接 `pushUrl` |
| `live.srs.play-base-url` | 准备接口用它和 `app`、`streamName` 拼接 `playUrl`；可为空 |
| `live.reconnect-window-seconds` | SRS 断流后的业务重连窗口；属于直播生命周期配置，因此继续放在 `live` 下 |
| `live.prepare-timeout-seconds` | 准备接口签发凭证后，允许等待首次有效 `on_publish` 的时间；默认 120 秒 |
| `live.push-token-seconds` | pt 有效时长，单位秒；用于计算载荷中的 `exp`，必须覆盖预期最长直播及断线重连时间，过期 pt 的重连会被拒绝 |

结束流程会通过 `http_apis` 查询发布流并强制断开推流客户端。`publish-token-key`、`push-base-url` 和 `app` 为生成、校验 pt 的必需配置；`play-base-url` 可为空。
`push-token-seconds` 不能小于 `prepare-timeout-seconds`，否则准备接口会拒绝创建场次，避免场次仍允许等待但凭证已经提前过期。

## 三、开播前检查

### 1. 检查主播开播资格

```http
GET /api/v1/app/live/anchor/live/check
Authorization: Bearer <APP Token>
```

后端会检查：

- 主播申请已经审核通过；
- 主播身份状态正常；
- 主播没有处于临时或永久封禁状态；
- `livePermission` 已开启；
- 风险等级允许开播；
- 如果当前环境要求主播认证，还会检查认证是否已经通过。

该接口只检查主播资格，不创建直播间，也不判断直播间当前状态。直播间不存在时的补建、直播间是否正常、是否已有活动场次等检查，由准备开播接口完成。

### 2. 查询自己的直播间

```http
GET /api/v1/app/live/room/info
Authorization: Bearer <APP Token>
```

审核通过时系统通常已经创建直播间。该接口返回房间当前资料，以及存在时的当前活动场次。

### 3. 查询可用直播分类

```http
GET /api/v1/app/live/category/list
```

准备开播时提交的 `categoryId` 必须指向启用状态的直播分类。

## 四、准备开播

调用：

```http
POST /api/v1/app/live/room/session/prepare
Authorization: Bearer <APP Token>
Content-Type: application/json
```

请求示例：

```json
{
  "categoryId": 12,
  "title": "今天的第一场直播",
  "coverUrl": "https://cdn.example.com/live-cover.jpg",
  "visibility": 1
}
```

`visibility` 取值：

| 值 | 含义 |
|---:|---|
| `0` | 私密 |
| `1` | 公开 |
| `2` | 仅关注者 |

成功响应示例：

```json
{
  "code": 0,
  "data": {
    "roomNo": "1500001",
    "sessionNo": "20290806135612345-1500001-1500001",
    "streamName": "1500001",
    "prepareDeadlineAt": 1880715720000,
    "publishToken": "v1_...",
    "pushUrl": "rtmp://example.com/live/1500001?pt=v1_...",
    "playUrl": "https://example.com/live/1500001"
  },
  "msg": "场次已准备"
}
```

`sessionNo` 格式为：

```text
yyyyMMddHHmmssSSS-anchorNo-roomNo
```

例如：

```text
20290806135612345-1500001-1500001
```

其中时间部分精确到毫秒。生成时会查询包含软删除记录在内的历史编号；如果同一毫秒发生碰撞，会顺延逻辑毫秒重新生成，数据库的 `uk_live_session_no` 唯一索引作为最后一道并发兜底。

后端在同一个事务中：

1. 创建 `live_session`，状态为准备中 `0`，写入 `prepare_deadline_at`；
2. 把分类、标题和封面写入场次快照；
3. 更新 `live_room.current_session_id`；
4. 把 `live_room.live_status` 更新为准备中 `1`；
5. 组装 pt V1 载荷，使用 `SHA-256(live.publish-token-key)` 派生的 AES-256 密钥做 GCM 加密，再进行 Base64URL 编码；数据库只保存最终 `publishToken` 的 SHA-256 哈希；
6. 返回推流地址和播放地址。

pt V1 解密后的 JSON 载荷为：

```json
{
  "ver": 1,
  "scope": "live:publish",
  "token_id": "82fd10bcfa8c4e28",
  "session_no": "20290806135612345-1500001-1500001",
  "app": "live",
  "vhost": "example.com",
  "stream": "1500001",
  "credential_version": 1,
  "iat": 1790204400,
  "nbf": 1790204340,
  "exp": 1790290800
}
```

- `token_id` 为 8 字节安全随机数的 16 位十六进制文本；
- `app` 来自 `live.srs.app`，`vhost` 来自 `live.srs.push-base-url` 的域名，`stream` 来自 `live_room.stream_name`；
- `iat/nbf/exp` 单位都是 Unix 秒，`nbf = iat - 60`，`exp = iat + live.push-token-seconds`；
- AES-256-GCM 密钥为 `SHA-256(live.publish-token-key)`，输出字节为 `12 字节 nonce + GCM 密文及鉴别标签`；
- 合并后使用无填充 Base64URL 编码，最终添加 `v1_` 前缀。

准备完成后：

```text
live_session.status = 0
live_session.prepare_deadline_at = 当前时间 + prepare-timeout-seconds
live_session.started_at = 0
live_room.live_status = 1
live_room.live_started_at = 0
```

需要注意：

- 同一直播间最多只能有一个活动场次；
- 活动场次存在时再次准备会返回“直播间已有活动场次”；
- `publishToken` 是不透明的加密凭证，只在本次准备响应中返回一次；
- `GET /room/session/current` 不会重新返回 `publishToken`；
- 如果丢失 `publishToken`，应先取消准备中的场次，再重新准备开播。

## 五、准备中

查询当前场次：

```http
GET /api/v1/app/live/room/session/current
Authorization: Bearer <APP Token>
```

没有活动场次时，当前实现返回成功响应且 `data` 为 `null`；需要查看上一场直播时，应调用公开详情接口读取 `latestSession`，或者调用历史场次接口。

准备中关键响应：

```json
{
  "sessionNo": "20290806135612345-1500001-1500001",
  "status": 0,
  "prepareDeadlineAt": 1880715720000,
  "startedAt": 0,
  "endedAt": 0
}
```

公开详情也能查询准备中的房间：

```http
GET /api/v1/app/live/room/detail?roomNo=1500001
```

关键响应：

```json
{
  "liveStatus": 1,
  "latestSession": {
    "sessionNo": "20290806135612345-1500001-1500001",
    "status": 0,
    "streamInfo": {},
    "startedAt": 0
  }
}
```

准备中的房间不会进入公开直播列表。公开列表只展示 `live_room.live_status = 2` 的直播中房间。

达到 `prepareDeadlineAt` 后，`LiveSessionLifecycle` 会把场次直接改为 `Cancelled`，结束原因为“准备开播超时”，并释放 `current_session_id`。准备超时没有真正开播，因此不调用 SRS、不进入 `Ending`、不累计直播次数或时长。`on_publish` 自身也会校验该截止时间，所以即使扫描尚未执行，过期凭证也不能开播。

## 六、开始直播

### 正式环境

主播使用 OBS 推送准备接口返回的 `pushUrl`。SRS 收到流以后调用：

```http
POST /api/v1/app/live/hook/publish
Content-Type: application/json
```

请求示例：

```json
{
  "server_id": "srs-1",
  "action": "on_publish",
  "client_id": "client-1",
  "stream_id": "stream-1",
  "stream": "1500001",
  "param": "?pt=准备接口返回的publishToken"
}
```

后端校验：

- pt 是否能通过 AES-256-GCM 完整性校验；
- `ver/scope/token_id/iat/nbf/exp` 是否有效；
- pt 中的 `session_no/app/vhost/stream/credential_version` 是否与当前配置、回调和数据库活动场次一致；
- `stream` 是否对应有效直播间；
- `publishToken` 是否匹配数据库中保存的哈希；
- 房间、主播、权限和风险状态是否允许开播；
- 准备场次是否仍在 `prepare_deadline_at` 之前；
- 当前场次是否处于准备中，或是否处于允许重连的直播中状态。

首次有效推流后：

```text
live_session.status = 1
live_session.prepare_deadline_at = 0
live_session.started_at = 当前Unix毫秒时间
live_room.live_status = 2
live_room.live_started_at = live_session.started_at
```

### `html-4主播开播.html` 本地联调

本地调试步骤：

1. 填写 APP Bearer Token；
2. 加载分类并填写本场标题、封面和可见范围；
3. 点击“准备开播”，页面自动保存 `sessionNo`、`streamName` 和 `publishToken`；
4. 点击“开始直播”；
5. 再点击“当前场次”确认场次已经变成直播中 `status=1`。

“开始直播”按钮只用于本地联调，它等同于模拟一次 SRS `on_publish`。正式环境由 OBS 推流和 SRS 回调触发，Hook 接口由部署层来源 IP 白名单保护。

## 八、直播统计更新

可信统计服务调用：

```http
POST /api/v1/app/live/hook/session/stats
Content-Type: application/json
```

请求示例：

```json
{
  "sessionNo": "20290806135612345-1500001-1500001",
  "viewCount": 320,
  "viewerCount": 260,
  "peakOnlineCount": 120,
  "likeCount": 1500,
  "giftCount": 20,
  "giftCoinAmount": 6800,
  "giftUserCount": 8
}
```

统计数据写入 `live_session`。公开详情返回观看次数、去重观看人数、峰值在线人数、点赞数和已清洗的 `streamInfo`；不公开 `publishIp`、礼物金币金额、断流信息、失败原因和结算控制字段。首次有效 `on_publish` 会把 SRS 请求中的 `ip` 写入 `publishIp`；`streamInfo` 尚未实现采集，默认返回空对象 `{}`。

## 九、短暂断流与重连

SRS 断流时调用：

```http
POST /api/v1/app/live/hook/unpublish
Content-Type: application/json
```

请求示例：

```json
{
  "server_id": "srs-1",
  "action": "on_unpublish",
  "client_id": "client-1",
  "stream_id": "stream-1",
  "stream": "1500001"
}
```

系统不会立即结束场次，而是更新：

```text
live_session.last_unpublish_at
live_session.reconnect_deadline_at
live_session.disconnect_count
```

服务端会先比较当前场次保存的 `server_id + client_id + stream_id`。新连接重连成功后，旧连接迟到的 `on_unpublish` 会被幂等忽略；直播仍活跃时，不同连接的迟到或竞争性 `on_publish` 也不能覆盖当前发布者身份。

默认重连窗口约为 20 秒，以实际配置为准：

```yaml
live:
  reconnect-window-seconds: 20
```

重连窗口内重新收到合法 `on_publish` 时：

- 继续使用原 `sessionNo`；
- 不创建新场次；
- 首次 `startedAt` 不变；
- 清空 `reconnectDeadlineAt`；
- 房间继续保持直播中。

因此 OBS 短暂网络抖动不会被拆成两场直播。

## 十、主播主动结束

调用：

```http
POST /api/v1/app/live/room/session/end
Authorization: Bearer <APP Token>
```

该接口没有请求体。服务端从 APP JWT 取得主播身份，通过其唯一直播间的 `current_session_id` 定位当前活动场次。当前没有活动场次时返回“当前没有活动直播场次”。

不同阶段的处理：

### 准备中取消

```text
live_session.status = 4
live_room.live_status = 0
live_room.current_session_id = 0
```

场次没有真正开播，因此不会更新 `live_room.last_session_id`，也不会覆盖上一场真实直播。

### 直播中结束

```text
live_session.status = 2
live_room.live_status = 3
```

场次进入结束中，等待后台任务最终结算。

事务提交后接口会同步尝试调用 SRS 强制断流。成功或确认流不存在时会立即结算为已结束；失败或超时时保留结束中，由定时任务重试。

管理员强制结束使用：

```http
POST /api/v1/admin/live/session/end
Authorization: <后台JWT>
```

请求示例：

```json
{
  "sessionId": 123,
  "reason": "后台人工终止直播"
}
```

后台接口按数据库内部 `sessionId` 操作；该主键只暴露在管理后台，不提供给 APP 客户端。主播端结束接口不传 `sessionNo`，始终操作当前登录主播的活动场次。

## 十一、断流超时

如果超过重连截止时间仍未恢复，后台任务会把直播中场次更新为结束中：

```text
live_session.status = 2
live_room.live_status = 3
```

断流超时的 `endedAt` 优先使用最近一次实际断流时间，不把最后等待重连的窗口计入直播时长。

## 十二、最终结算

当前注册了内置 `LiveSessionLifecycle` 定时任务。数据库表结构就绪后会异步立即扫描一次，之后默认每 5 秒执行 `ProcessPendingSessions`。任务处理准备超时、断线重连超时，并通过数据库租约认领结束中场次；只有 SRS 成功或确认流不存在后才完成结算。

结算完成后：

```text
live_session.status = 3
live_session.duration_ms = ended_at - started_at
live_session.stats_finalized_at = 结算时间

live_room.live_status = 0
live_room.current_session_id = 0
live_room.last_session_id = 本场live_session.id
live_room.live_started_at = 0
```

同时更新主播累计数据：

```text
live_anchor.total_live_count
live_anchor.total_live_duration_ms
live_anchor.total_view_count
live_anchor.max_online_count
live_anchor.last_live_end_at
```

`durationMs` 表示逻辑直播时长，等于 `endedAt - startedAt`，允许包含重连成功前的短暂断流时间。

## 十三、结束后的接口表现

场次结算后，房间从公开直播列表消失，但公开详情仍可以查询房间和上一场直播：

```http
GET /api/v1/app/live/room/detail?roomNo=1500001
```

关键响应：

```json
{
  "liveStatus": 0,
  "latestSession": {
    "sessionNo": "20290806135612345-1500001-1500001",
    "status": 3,
    "streamInfo": {},
    "startedAt": 1880715600000,
    "endedAt": 1880719200000,
    "durationMs": 3600000,
    "viewCount": 1680,
    "viewerCount": 1200,
    "peakOnlineCount": 320,
    "likeCount": 9800
  }
}
```

如果主播从未完成过直播：

```json
{
  "liveStatus": 0,
  "latestSession": {}
}
```

查询主播自己的历史场次：

```http
GET /api/v1/app/live/room/session/history?page=1&pageSize=20
Authorization: Bearer <APP Token>
```

历史接口会包含已结束、已取消等场次，可以通过 `status` 查询参数过滤。

## 十五、常见问题

### 1. 准备接口提示已有活动场次

先调用 `/room/session/current`。准备中场次可以通过 `/room/session/end` 取消；直播中场次需要先请求结束并等待最终结算。

### 2. “开始直播”提示缺少 `publishToken`

`publishToken` 只在准备响应中返回一次。刷新页面或丢失凭证后不能通过查询接口找回，应取消当前准备场次并重新准备。

### 3. `on_publish` 返回推流凭证无效

检查：

- OBS 或测试页面是否使用本次准备返回的 `streamName`；
- `param` 是否携带本次准备返回的 `publishToken`；
- 是否重复准备过场次，导致旧凭证失效；
- SRS 是否完整透传 URL 查询参数。

### 4. 已经准备，但公开列表看不到

这是正常行为。准备中的 `liveStatus=1`，公开列表只展示直播中的 `liveStatus=2`。收到合法 `on_publish` 后才会进入公开列表。

### 5. OBS 短暂断流后为什么还是同一个场次

系统有短暂重连窗口。窗口内恢复会继续原 `sessionNo`，这是为了避免网络抖动错误产生多个直播场次。

### 6. 已经下播，但房间仍显示结束中

结束中是可观察、可恢复的中间状态。内置任务默认每 5 秒重试，但会遵守 `stop_next_retry_at` 的退避时间；长期不变时检查 `stop_last_error`、SRS HTTP API 配置以及 `LiveSessionLifecycle` 任务日志。

### 7. 未开播时为什么 `latestSession` 仍有内容

如果主播以前完成过直播，`latestSession` 返回最近一次已结束场次；只有从未完成过直播时才返回空对象 `{}`。

## 十六、安全边界

- APP 和公开接口不返回 `live_room.id`、`live_session.id`、`anchor_id`、`room_id`、`current_session_id`、`last_session_id`；
- `publishToken` 加密字符串只在准备响应中返回一次，服务端只保存最终 Token 的哈希；
- Hook 接口必须由部署层真实来源 IP/CIDR 白名单保护；
- `live.publish-token-key` 只能保存在 Go 服务端，不得配置到 SRS、代理或客户端；
- 公开详情不返回断流重连控制字段、失败原因、结算时间或礼物金额；
- `publishIp` 只允许管理后台场次列表和详情查看，APP 与公开接口都不返回；
- `streamInfo` 是公开白名单 JSON，不能直接透传 SRS 原始对象中的 IP、token 或内部连接标识；
- 客户端应使用 `roomNo`、`anchorNo` 和 `sessionNo`，不能依赖数据库内部主键；
- `streamName` 是稳定流名称，不是推流凭证，不能代替 `publishToken`。
