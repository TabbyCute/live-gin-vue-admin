# 定时任务说明

本文说明当前后端注册的全部定时任务、执行周期、扫描表、并发保护、失败行为和配置方式。

## 一、任务注册位置

所有应用内定时任务当前统一在：

```text
server/initialize/timer.go
```

应用在数据库表结构初始化完成后调用 `initialize.Timer()` 注册。定时器使用 `robfig/cron/v3` 并启用秒级解析。各直播任务注册成功后都会异步立即执行一次，服务重启无需等待首个周期。

当前共有五个定时任务：

| Cron 名称 | 周期 | 作用 |
|---|---|---|
| `ClearDB` | `@daily` | 清理过期操作日志和 JWT 黑名单 |
| `LiveSessionLifecycle` | 启动立即一次，之后默认每 5 秒 | 只处理准备开播超时和断线重连超时，不请求 SRS |
| `LiveSessionStop` | 生命周期启动补偿后立即一次，之后默认每 5 秒 | 有界并发处理结束中场次的 SRS 断流和最终结算 |
| `LiveStreamReadiness` | 启动立即一次，之后默认每 1 秒扫描到期任务 | 按指数退避批量查询 SRS；取得真实宽高后进入直播中，默认 15 秒仍未就绪则结束推流并取消场次 |
| `LiveStreamReconciliation` | 启动立即一次，之后按配置周期 | 批量核对直播中的 SRS 发布流，连续缺失达到阈值后进入重连窗口 |

## 二、ClearDB

### 周期

```text
@daily
```

即每天执行一次，实际时区使用服务进程所在时区。

### 执行方法

```text
task.ClearTable(global.GVA_DB)
```

实现位置：

```text
server/task/clearTable.go
```

### 清理内容

| 表 | 比较字段 | 保留时间 |
|---|---|---:|
| `sys_operation_records` | `created_at` | 2160 小时，即 90 天 |
| `jwt_blacklists` | `created_at` | 168 小时，即 7 天 |

执行的逻辑相当于：

```sql
DELETE FROM 表名
WHERE created_at < 当前时间 - 保留时间;
```

该任务与直播业务无关，不读取或修改 `live_room`、`live_session`。

### 失败行为

任意删除操作失败时，本轮任务返回错误并输出日志，不会终止应用。下一天会再次执行。当前实现没有单独的失败重试任务。

## 三、LiveSessionLifecycle

### 周期和配置

配置位于 `live`：

```yaml
live:
  max-concurrent-streams: 10000
  prepare-timeout-seconds: 120
  stream-ready-timeout-seconds: 15
  stream-ready-scan-interval-seconds: 1
  stream-ready-retry-base-seconds: 1
  stream-ready-retry-max-seconds: 4
  stream-ready-batch-size: 1000
  stream-ready-max-batches-per-run: 10
  state-transition-concurrency: 16
  stream-reconcile-batch-size: 1000
  stream-reconcile-max-batches-per-run: 10
  srs-snapshot-cache-milliseconds: 1500
  task-leader-enabled: true
  task-leader-fail-open: true
  task-leader-lease-seconds: 60
  end-scan-interval-seconds: 5
  end-scan-batch-size: 1000
  end-scan-max-batches-per-run: 10
  end-stop-batch-size: 1000
  end-stop-max-batches-per-run: 10
  end-stop-concurrency: 8
  end-retry-base-seconds: 5
  end-retry-max-seconds: 60
```

| 配置 | 默认值 | 说明 |
|---|---:|---|
| `max-concurrent-streams` | 10000 | 控制面容量目标；各任务的有效批次数不会低于覆盖该数量所需的批次数，代码最大限制 100000 |
| `prepare-timeout-seconds` | 120 | 准备接口签发凭证后，允许等待首次有效发布的秒数 |
| `stream-ready-timeout-seconds` | 15 | 收到有效 `on_publish` 后等待 SRS 返回有效宽高的硬截止时间 |
| `stream-ready-scan-interval-seconds` | 1 | 就绪任务扫描间隔；只有到达各场次退避时间时才会请求 SRS |
| `stream-ready-retry-base-seconds` | 1 | 首次流信息重试间隔 |
| `stream-ready-retry-max-seconds` | 4 | 流信息指数退避最大间隔 |
| `stream-ready-batch-size` | 1000 | 流就绪任务单个数据库批次最多处理的场次；代码最大限制 1000 |
| `stream-ready-max-batches-per-run` | 10 | 单次 Cron 连续推进的就绪批次下限；有效值会自动补足到容量目标 |
| `state-transition-concurrency` | 16 | 生命周期和就绪落库的固定 worker 数；代码最大限制 64 |
| `stream-reconcile-batch-size` | 1000 | 直播中对账单个数据库批次的场次；代码最大限制 1000 |
| `stream-reconcile-max-batches-per-run` | 10 | 单次 Cron 连续处理的对账批次下限；批次间复用同一份 SRS 快照 |
| `srs-snapshot-cache-milliseconds` | 1500 | readiness、reconcile 和多实例共享 SRS 发布流快照的最大新鲜时间；代码限制 100～5000 毫秒 |
| `task-leader-enabled` | true | 是否通过 Redis 为每类直播定时任务选出单执行实例 |
| `task-leader-fail-open` | true | Redis Leader 不可用时是否由各实例有界降级执行；数据库租约/CAS继续防重复，错误日志继续告警 |
| `task-leader-lease-seconds` | 60 | Leader 租约时间；执行期间每三分之一租期自动续约，代码限制 10～600 秒 |
| `end-scan-interval-seconds` | 5 | 生命周期扫描与独立 SRS 收尾任务的执行间隔，秒 |
| `end-scan-batch-size` | 1000 | 准备和重连生命周期单个数据库批次的场次 |
| `end-scan-max-batches-per-run` | 10 | 准备和重连任务单次 Cron 的批次下限；有效值会自动补足到容量目标 |
| `end-stop-batch-size` | 1000 | SRS 收尾任务单个数据库批次的结束中场次；代码最大限制 1000 |
| `end-stop-max-batches-per-run` | 10 | SRS 收尾单次 Cron 的批次下限；有效值会自动补足到容量目标 |
| `end-stop-concurrency` | 8 | 单实例同时停止 SRS 推流的最大请求数；小于 1 按 8，代码最大限制 64 |
| `end-retry-base-seconds` | 5 | SRS 失败后的首次重试间隔 |
| `end-retry-max-seconds` | 60 | 指数退避最大间隔 |

配置值小于等于 0 时使用代码默认值。
`push-token-seconds` 必须不小于 `prepare-timeout-seconds`；否则准备接口不会创建场次。

生产环境当前关闭 AutoMigrate。上线任务前必须先执行 `documents/live_room_session.sql` 中的存量表升级，确保 `stream_ready_deadline_at`、`stream_probe_*`、停止控制字段及对应索引已存在；否则任务会持续报数据库缺列错误。

### 执行入口

```text
RoomService.ProcessPendingSessions(time.Now().UnixMilli())
```

### 扫描哪张表

只扫描：

```text
live_session
```

不会遍历 `live_room`。只有在处理某个具体场次时，才根据 `room_id` 按主键读取或更新对应直播间；最终结算时再根据 `anchor_id` 按主键更新主播累计数据。

### 第一阶段：处理准备开播超时

查询条件：

```sql
SELECT id
FROM live_session
WHERE status = 0
  AND srs_stream_id = ''
  AND prepare_deadline_at <= 当前毫秒时间戳
ORDER BY prepare_deadline_at, id
LIMIT end-scan-batch-size;
```

使用联合索引：

```text
idx_live_session_prepare_timeout(status, prepare_deadline_at)
```

命中的准备中场次会直接改为 `Cancelled`，写入“准备开播超时”，清除房间当前场次并恢复未开播。它们从未成功发布，因此不访问 SRS、不进入 `Ending`、不累计直播次数或时长。升级前遗留且截止时间为 `0` 的准备场次也会被首次启动扫描清理。

超时处理会重新锁定并检查房间、场次；如果并发 `on_publish` 已经先写入当前 SRS 连接，扫描会幂等跳过，改由流就绪任务等待真实宽高。反过来，如果超时取消先提交，后到的发布回调会被拒绝。

### 第二阶段：处理重连超时

查询条件：

```sql
SELECT id
FROM live_session
WHERE status = 1
  AND reconnect_deadline_at > 0
  AND reconnect_deadline_at <= 当前毫秒时间戳
ORDER BY reconnect_deadline_at, id
LIMIT end-scan-batch-size;
```

使用联合索引：

```text
idx_live_session_reconnect(status, reconnect_deadline_at)
```

查到的场次会：

- 从 `Living` 修改为 `Ending`；
- 结束原因修改为“断流超过重连窗口”；
- `ended_at` 优先使用最后一次 `on_unpublish` 时间；
- 写入停止请求与首次重试时间；
- 房间修改为 `Ending`。

结束状态提交后由独立的 `LiveSessionStop` 处理。启动补偿时两个任务按此顺序连续执行；周期运行时二者相互独立，因此 SRS 超时不会拖住后续生命周期扫描，最迟在下一个收尾扫描周期开始处理。

## 四、LiveSessionStop

### 处理结束中场次

查询条件：

```sql
SELECT id
FROM live_session
WHERE status = 2
  AND stop_next_retry_at <= 当前毫秒时间戳
ORDER BY stop_next_retry_at, id
LIMIT end-stop-batch-size;
```

使用联合索引：

```text
idx_live_session_end_retry(status, stop_next_retry_at)
```

因此这是索引范围查询，不是全表扫描。绝大多数历史场次为 `Ended`，不会进入扫描范围。

任务在单轮内最多领取容量目标对应的 ID，但始终只使用固定大小的 worker 池。标准 SRS 客户端会先用一次分页快照定位全部发布者，再固定并发执行必要的 `DELETE clients/{cid}`；不会为每个场次重复查询流列表。SRS 列表本身不可用时，整批会在一次快照请求失败后统一写入退避，不会再放大为 1 万个超时请求。下一次 Cron 触发若发现上一轮仍在运行会直接跳过，不会叠加 goroutine 或内存队列。

每个场次的处理顺序：

1. MySQL/PostgreSQL 使用 `FOR UPDATE SKIP LOCKED` 批量认领数据库租约，其他数据库使用逐行 CAS 兼容路径；
2. 一次批量读取 `room_id + stream_name`；
3. 一次分页读取 SRS 流列表，优先按保存的 `srs_stream_id` 匹配；
4. ID 已失效时在同一份快照内按 `vhost + app + stream` 匹配活动发布流；
5. 流不存在时直接最终结算；
6. 流存在时取得 `publish.cid` 并调用 SRS 删除客户端；
7. SRS 成功，或删除时返回客户端不存在的 `code = 2049`，把场次结算为 `Ended`；
8. SRS 失败或超时时保持 `Ending`，写入错误并安排下一次重试。

详细状态变化见 [直播间关闭流程.md](./直播间关闭流程.md)。

## 五、LiveStreamReadiness

### 执行入口和状态条件

```text
RoomService.ProcessStreamReadiness(time.Now().UnixMilli())
```

`on_publish` 只证明推流连接已经建立，不能证明 SRS 已经收到可用视频。首次回调会保存 SRS 连接身份并写入：

```text
stream_ready_deadline_at = 当前时间 + 15秒
stream_probe_attempts = 0
stream_probe_next_at = 当前时间
```

场次和房间仍保持准备中，`started_at` 仍为 `0`，`stream_info` 对外返回 `{}`。

每轮任务先用 `idx_live_session_stream_ready(status, stream_ready_deadline_at)` 查询已经超过硬截止时间的场次，再用 `idx_live_session_stream_probe(status, stream_probe_next_at)` 查询到达下一次探测时间的场次。超过截止时间的记录优先处理，不能被普通探测积压挤到下一轮。

### 批量查询和就绪条件

同一轮所有成功认领的场次只调用一次 SRS `/api/v1/vhosts` 和分页 `/api/v1/streams`，随后在内存中按 `srs_stream_id` 匹配，不会为每个直播间单独发请求。只有以下条件全部满足才正式开播：

- `publish.active = true`；
- SRS stream ID、逻辑 vhost、app、stream 均与当前数据库连接一致；
- `video.width > 0`；
- `video.height > 0`。

满足后在数据库事务中写入仅包含编码、宽高、音频参数和采集时间的公开白名单 `stream_info`，并同时完成：

```text
live_session.status: Preparing -> Living
live_session.started_at = 当前完成时间
live_room.live_status: Preparing -> Living
live_room.live_started_at = 当前完成时间
```

SRS 原始响应中的 IP、鉴权参数和客户端内部标识不会进入 `stream_info`。

### 退避、硬截止和失败行为

默认探测间隔为 `1、2、4、4……` 秒，下一次时间永远不会超过 `stream_ready_deadline_at`。15 秒窗口内通常最多查询 5 次；扫描任务每秒运行并不等于每秒查询每条流。

单次 SRS 请求的超时会取以下两者中的较小值：

```text
live.srs.api-request-timeout-seconds
最早到期场次距离 stream_ready_deadline_at 的剩余时间
```

请求完成后还会按真实完成时间再次检查硬截止。第 15 秒前发起、但第 15 秒后才返回的有效尺寸不能把场次提升为直播中。周期调度可能让实际断流动作比截止时间晚最多一个扫描周期，但业务不会接受截止时间后的成功开播。

SRS 暂无流、只有一个尺寸、`publish.active=false`、API 超时或解析失败时，场次保持原状态并记录最近错误。达到硬截止后：

1. 有发布连接的准备场次进入 `Ending`；
2. 使用现有停止租约断开 SRS 发布端；
3. 确认流已停止后结算为 `Cancelled`；
4. `started_at`、直播次数和直播时长均不增加；
5. 停止结果未知时保持 `Ending`，阻止新场次创建，并由结束任务继续退避重试。

准备阶段收到匹配的 `on_unpublish` 时会清除连接身份和探测字段，旧的 SRS 快照无法再把它提升为直播中；主播仍可在原准备期限内重新推流。

## 六、结束重试规则

默认重试间隔为：

```text
第 1 次失败：5 秒
第 2 次失败：10 秒
第 3 次失败：20 秒
第 4 次失败：40 秒
第 5 次及以后：60 秒
```

具体间隔由 `end-retry-base-seconds` 和 `end-retry-max-seconds` 控制。

定时任务只查询 `stop_next_retry_at <= 当前时间` 的场次。因此即使任务每 5 秒运行，也不会每次都请求所有结束中场次。

系统没有因为达到某个重试次数就直接把场次强制改为 `Ended`。无法确认 SRS 已经停止时，场次应继续保持 `Ending`，以避免业务状态与媒体状态不一致。

## 七、并发和重复执行保护

### 同一进程

生命周期、SRS 收尾、流就绪和直播中对账任务分别使用各自的 `sync.Mutex.TryLock()`。同一种任务的启动扫描和周期扫描重叠时，后一轮直接跳过，不会在同一进程中堆积 goroutine；不同任务可以并行处理各自的状态条件。即使 SRS 收尾请求全部超时，纯数据库的准备/重连超时扫描仍会继续运行。

### 多个服务实例

启用 `task-leader-enabled` 后，每一类任务使用独立 Redis Key 获取 Leader 租约。相同任务在所有后端实例中同一时刻只有一个执行者；不同类型任务仍可并行。长任务每三分之一租期续约，释放时用随机 token 比较后删除，旧实例不会误删新 Leader 的租约。Redis 获取或续约失败时跳过或终止该轮 Leader 身份并记录错误，不会让所有实例同时降级执行。

Redis Leader 用于降低重复扫描和重复 SRS 快照流量，下面的数据库条件认领仍然保留，作为租约丢失、进程暂停或人工请求并发时的最终一致性保护。

每个场次在调用 SRS 前执行条件更新：

```sql
UPDATE live_session
SET stop_attempts = stop_attempts + 1,
    stop_next_retry_at = 租约截止时间
WHERE id = ?
  AND status = 2
  AND stop_next_retry_at <= 当前时间;
```

只有成功更新一行的实例可以继续调用 SRS。其他实例或人工请求无法同时认领同一场次。

租约时长为：

```text
SRS API 请求超时时间 + 2 秒
```

如果处理进程崩溃，租约到期后其他任务可以继续处理，不会永久丢失。

流就绪任务同样通过 `stream_probe_next_at` 条件更新认领处理权。普通探测只有一个实例能成功认领；硬截止处理即使被多个实例同时观察到，事务中的状态条件也只允许一个实例进入 `Ending`，后续断流仍由 `stop_next_retry_at` 租约保证单执行者。

### 与人工结束并发

主播或管理员主动结束时也使用相同租约：

- 人工请求先认领：定时任务跳过；
- 定时任务先认领：人工请求确认结束意图已经保存后返回，任务继续处理；
- SRS 成功和最终结算均为幂等操作；
- 主播累计次数、时长和观看量只会增加一次。

## 八、SRS请求配置

```yaml
live:
  srs:
    http_apis: http://127.0.0.1:1985
    api-username: admin
    api-password: "从环境变量注入"
    api-request-timeout-seconds: 3
    snapshot-page-size: 5000
    snapshot-max-streams: 20000
```

`api-request-timeout-seconds` 默认 3 秒。它限制每个 SRS HTTP 请求；批量收尾使用 60 秒数据库租约并保持幂等，避免正常批处理期间被重复认领。

`snapshot-page-size` 控制一次 `/streams` 分页数量，代码硬上限 5000；`snapshot-max-streams` 默认 20,000，代码硬上限 100,000。达到上限后客户端会额外探测一条；如果仍有数据则整轮失败，绝不会拿截断列表判断直播已断流。

如果 `http_apis`、认证或网络配置错误：

- 当前场次保持 `Ending`；
- `stop_last_error` 保存最近错误；
- 定时任务继续按退避时间重试；
- 其他场次仍会在同一轮继续处理；
- 本轮汇总错误会输出为 `live session stop timer error`，最多展示 5 种、每种最多 500 个字符，避免大量同类故障放大日志。

## 九、性能说明

`LiveSessionLifecycle` 每个批次执行两类带联合索引的 ID 查询：

1. 查找准备开播超时的 `Preparing` 场次；
2. 查找重连超时的 `Living` 场次。

这些查询不加载大 JSON 字段，也不访问 SRS，并在固定 worker 中推进。每轮按 1000×10 覆盖 1 万路，失败项通过键集游标跳过，不会在本轮反复占据队头。`LiveSessionStop` 批量认领到达重试时间的 `Ending` 场次，再复用一次 SRS 快照；有界 worker 池限制断流和最终结算并发。

`LiveStreamReadiness` 每批先查硬截止，再查退避到期。MySQL/PostgreSQL 用 `FOR UPDATE SKIP LOCKED` 一次认领整批，避免 1 万路产生 1 万条认领 SQL；没有到期场次时不会访问 SRS，整轮最多 10 批并复用同一份有界分页流列表。readiness 与 reconcile 还会通过短时缓存共享快照：单实例无 Redis 时使用进程缓存，多实例启用 Redis 后使用分布式刷新锁；缓存超过新鲜期后绝不会继续用于断流判断，缓存聚合值硬上限 16 MiB。

直播中对账会把“流仍存在”“缺失但未达到阈值”的场次分别合并为条件批量 `UPDATE`。只有连续缺失达到阈值、需要进入重连窗口的场次才逐场开启锁事务，因此正常直播数量增长时，事务数量不再与场次数量线性增长。任务会按 `stream_reconcile_checked_at, id` 顺序连续领取 10 个批次，并在批次间复用同一份快照；默认配置一次 Cron 覆盖 10000 路。

性能注意事项：

- 不要删除生命周期、SRS 收尾、流就绪和直播中对账使用的联合索引；
- 批量大小不建议超过 1000；
- `end-stop-concurrency` 建议先保持 8；批量快照已消除逐场查询，不应仅为追赶外部故障积压而盲目调高；
- 不要把 SRS 请求放进数据库事务；
- SRS 故障时不要固定每 5 秒重试所有场次，应保留退避；
- 多实例部署应启用 Redis Leader，并保留 `task-leader-fail-open` 与数据库条件认领；Redis 故障时可能增加“实例数倍”的批量查询，但不会冻结状态机；
- 如果长期积压的 `Ending` 数量增长，应先排查 SRS 连通性，而不是无限提高批量大小。

仓库提供 `BenchmarkLiveStreamReconciliationCapacity`，可用 `go test ./service/live -run '^$' -bench BenchmarkLiveStreamReconciliationCapacity -benchtime=1x` 对 100、500、1000、5000、10000 路进行可重复的应用层基准。该基准使用 SQLite，只用于发现算法和 SQL 次数退化；生产容量结论仍必须使用 MySQL 8、真实 SRS 和实际网络执行压测。任何任务实际超过 `max-concurrent-streams` 时会返回 `直播定时任务待处理数量超过单轮容量`，不会静默积压。

## 十、日志和排查

定时任务注册失败时输出：

```text
add live session timer error: ...
```

任务执行失败时输出：

```text
live session timer error: ...
```

SRS 收尾任务失败时输出：

```text
live session stop timer error: ...
```

流就绪任务失败时输出：

```text
live stream readiness timer error: ...
```

排查结束任务积压：

```sql
SELECT id, session_no, status,
       stop_attempts, stop_next_retry_at, stop_last_error
FROM live_session
WHERE status = 2
ORDER BY stop_next_retry_at, id;
```

排查断线等待：

```sql
SELECT id, session_no, status,
       last_unpublish_at, reconnect_deadline_at
FROM live_session
WHERE status = 1
  AND reconnect_deadline_at > 0
ORDER BY reconnect_deadline_at, id;
```

排查准备超时积压：

```sql
SELECT id, session_no, status, prepare_deadline_at
FROM live_session
WHERE status = 0
ORDER BY prepare_deadline_at, id;
```

## 十一、新增定时任务时的约束

新增任务应继续在 `initialize.Timer()` 统一注册，并明确：

- 唯一 Cron 名称；
- 周期和时区；
- 扫描表及索引；
- 每轮批量上限；
- 是否允许同一进程重叠；
- 多实例如何竞争处理权；
- 外部调用超时；
- 失败重试和幂等规则；
- 日志与人工排查方式。

不能只用进程内 `goroutine` 或内存标记承载必须可靠执行的任务；服务重启后仍需能够从数据库状态恢复。
