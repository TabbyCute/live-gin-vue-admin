# 定时任务说明

本文说明当前后端注册的全部定时任务、执行周期、扫描表、并发保护、失败行为和配置方式。

## 一、任务注册位置

所有应用内定时任务当前统一在：

```text
server/initialize/timer.go
```

应用在数据库表结构初始化完成后调用 `initialize.Timer()` 注册。定时器使用 `robfig/cron/v3` 并启用秒级解析。`LiveSessionLifecycle` 注册成功后会异步立即执行一次，之后再按周期运行；因此服务重启后不会额外等待首个 5 秒周期。

当前共有两个定时任务：

| Cron 名称 | 周期 | 作用 |
|---|---|---|
| `ClearDB` | `@daily` | 清理过期操作日志和 JWT 黑名单 |
| `LiveSessionLifecycle` | 启动立即一次，之后默认每 5 秒 | 处理准备开播超时、断线重连超时，并重试结束中场次的 SRS 断流 |

## 二、ClearDB

### 周期

```text
@daily
```

即每天执行一次，实际时区使用服务进程所在时区。

### 执行方法

```text
task.ClearTable(global.GVA_DB)
```

实现位置：

```text
server/task/clearTable.go
```

### 清理内容

| 表 | 比较字段 | 保留时间 |
|---|---|---:|
| `sys_operation_records` | `created_at` | 2160 小时，即 90 天 |
| `jwt_blacklists` | `created_at` | 168 小时，即 7 天 |

执行的逻辑相当于：

```sql
DELETE FROM 表名
WHERE created_at < 当前时间 - 保留时间;
```

该任务与直播业务无关，不读取或修改 `live_room`、`live_session`。

### 失败行为

任意删除操作失败时，本轮任务返回错误并输出日志，不会终止应用。下一天会再次执行。当前实现没有单独的失败重试任务。

## 三、LiveSessionLifecycle

### 周期和配置

配置位于 `live`：

```yaml
live:
  prepare-timeout-seconds: 120
  end-scan-interval-seconds: 5
  end-scan-batch-size: 100
  end-retry-base-seconds: 5
  end-retry-max-seconds: 60
```

| 配置 | 默认值 | 说明 |
|---|---:|---|
| `prepare-timeout-seconds` | 120 | 准备接口签发凭证后，允许等待首次有效发布的秒数 |
| `end-scan-interval-seconds` | 5 | 定时任务执行间隔，秒 |
| `end-scan-batch-size` | 100 | 每类状态每轮最多读取的场次数量；代码最大限制 1000 |
| `end-retry-base-seconds` | 5 | SRS 失败后的首次重试间隔 |
| `end-retry-max-seconds` | 60 | 指数退避最大间隔 |

配置值小于等于 0 时使用代码默认值。
`push-token-seconds` 必须不小于 `prepare-timeout-seconds`；否则准备接口不会创建场次。

生产环境当前关闭 AutoMigrate。上线任务前必须先执行 `documents/live_room_session.sql` 中的存量表升级，确保 `prepare_deadline_at`、停止控制字段、`idx_live_session_prepare_timeout` 和 `idx_live_session_end_retry` 已存在；否则任务会持续报数据库缺列错误。

### 执行入口

```text
RoomService.ProcessPendingSessions(time.Now().UnixMilli())
```

### 扫描哪张表

只扫描：

```text
live_session
```

不会遍历 `live_room`。只有在处理某个具体场次时，才根据 `room_id` 按主键读取或更新对应直播间；最终结算时再根据 `anchor_id` 按主键更新主播累计数据。

### 第一阶段：处理准备开播超时

查询条件：

```sql
SELECT id
FROM live_session
WHERE status = 0
  AND prepare_deadline_at <= 当前毫秒时间戳
ORDER BY prepare_deadline_at, id
LIMIT end-scan-batch-size;
```

使用联合索引：

```text
idx_live_session_prepare_timeout(status, prepare_deadline_at)
```

命中的准备中场次会直接改为 `Cancelled`，写入“准备开播超时”，清除房间当前场次并恢复未开播。它们从未成功发布，因此不访问 SRS、不进入 `Ending`、不累计直播次数或时长。升级前遗留且截止时间为 `0` 的准备场次也会被首次启动扫描清理。

超时处理会重新锁定并检查房间、场次；如果并发 `on_publish` 已经先把状态改为 `Living`，扫描会幂等跳过。反过来，如果超时取消先提交，后到的发布回调会被拒绝。

### 第二阶段：处理重连超时

查询条件：

```sql
SELECT id
FROM live_session
WHERE status = 1
  AND reconnect_deadline_at > 0
  AND reconnect_deadline_at <= 当前毫秒时间戳
ORDER BY reconnect_deadline_at, id
LIMIT end-scan-batch-size;
```

使用联合索引：

```text
idx_live_session_reconnect(status, reconnect_deadline_at)
```

查到的场次会：

- 从 `Living` 修改为 `Ending`；
- 结束原因修改为“断流超过重连窗口”；
- `ended_at` 优先使用最后一次 `on_unpublish` 时间；
- 写入停止请求与首次重试时间；
- 房间修改为 `Ending`。

本轮任务随后会继续处理这些结束中场次，不需要固定等待到下一轮。

### 第三阶段：处理结束中场次

查询条件：

```sql
SELECT id
FROM live_session
WHERE status = 2
  AND stop_next_retry_at <= 当前毫秒时间戳
ORDER BY stop_next_retry_at, id
LIMIT end-scan-batch-size;
```

使用联合索引：

```text
idx_live_session_end_retry(status, stop_next_retry_at)
```

因此这是索引范围查询，不是全表扫描。绝大多数历史场次为 `Ended`，不会进入扫描范围。

每个场次的处理顺序：

1. 通过条件更新认领数据库租约；
2. 按 `room_id` 主键读取 `stream_name`；
3. 优先使用保存的 `srs_stream_id` 查询 SRS；
4. ID 失效时按 `vhost + app + stream` 查询活动发布流；
5. 流不存在时直接最终结算；
6. 流存在时取得 `publish.cid` 并调用 SRS 删除客户端；
7. SRS 成功后把场次结算为 `Ended`；
8. SRS 失败或超时时保持 `Ending`，写入错误并安排下一次重试。

详细状态变化见 [直播间关闭流程.md](./直播间关闭流程.md)。

## 四、重试规则

默认重试间隔为：

```text
第 1 次失败：5 秒
第 2 次失败：10 秒
第 3 次失败：20 秒
第 4 次失败：40 秒
第 5 次及以后：60 秒
```

具体间隔由 `end-retry-base-seconds` 和 `end-retry-max-seconds` 控制。

定时任务只查询 `stop_next_retry_at <= 当前时间` 的场次。因此即使任务每 5 秒运行，也不会每次都请求所有结束中场次。

系统没有因为达到某个重试次数就直接把场次强制改为 `Ended`。无法确认 SRS 已经停止时，场次应继续保持 `Ending`，以避免业务状态与媒体状态不一致。

## 五、并发和重复执行保护

### 同一进程

启动立即扫描和周期扫描共用 `sync.Mutex.TryLock()`。如果上一轮仍在运行，下一轮直接跳过，不会在同一进程中堆积并发扫描。

### 多个服务实例

每个场次在调用 SRS 前执行条件更新：

```sql
UPDATE live_session
SET stop_attempts = stop_attempts + 1,
    stop_next_retry_at = 租约截止时间
WHERE id = ?
  AND status = 2
  AND stop_next_retry_at <= 当前时间;
```

只有成功更新一行的实例可以继续调用 SRS。其他实例或人工请求无法同时认领同一场次。

租约时长为：

```text
SRS API 请求超时时间 + 2 秒
```

如果处理进程崩溃，租约到期后其他任务可以继续处理，不会永久丢失。

### 与人工结束并发

主播或管理员主动结束时也使用相同租约：

- 人工请求先认领：定时任务跳过；
- 定时任务先认领：人工请求确认结束意图已经保存后返回，任务继续处理；
- SRS 成功和最终结算均为幂等操作；
- 主播累计次数、时长和观看量只会增加一次。

## 六、SRS请求配置

```yaml
live:
  srs:
    http_apis: http://127.0.0.1:1985
    api-username: admin
    api-password: "从环境变量注入"
    api-request-timeout-seconds: 3
```

`api-request-timeout-seconds` 默认 3 秒。它同时影响单次任务的最长网络等待和数据库处理租约时长。

如果 `http_apis`、认证或网络配置错误：

- 当前场次保持 `Ending`；
- `stop_last_error` 保存最近错误；
- 定时任务继续按退避时间重试；
- 其他场次仍会在同一轮继续处理；
- 本轮汇总错误会输出为 `live session timer error`。

## 七、性能说明

直播任务每轮最多执行三次带联合索引的 ID 查询：

1. 查找准备开播超时的 `Preparing` 场次；
2. 查找重连超时的 `Living` 场次；
3. 查找到达重试时间的 `Ending` 场次。

查询不加载大 JSON 字段，也不对历史已结束数据排序。只有认领成功的少量场次才会读取房间并访问 SRS。

性能注意事项：

- 不要删除三个联合索引；
- 批量大小不建议超过 1000；
- 不要把 SRS 请求放进数据库事务；
- SRS 故障时不要固定每 5 秒重试所有场次，应保留退避；
- 多实例部署必须保留数据库条件认领，不能只依赖进程锁；
- 如果长期积压的 `Ending` 数量增长，应先排查 SRS 连通性，而不是无限提高批量大小。

## 八、日志和排查

定时任务注册失败时输出：

```text
add live session timer error: ...
```

任务执行失败时输出：

```text
live session timer error: ...
```

排查结束任务积压：

```sql
SELECT id, session_no, status,
       stop_attempts, stop_next_retry_at, stop_last_error
FROM live_session
WHERE status = 2
ORDER BY stop_next_retry_at, id;
```

排查断线等待：

```sql
SELECT id, session_no, status,
       last_unpublish_at, reconnect_deadline_at
FROM live_session
WHERE status = 1
  AND reconnect_deadline_at > 0
ORDER BY reconnect_deadline_at, id;
```

排查准备超时积压：

```sql
SELECT id, session_no, status, prepare_deadline_at
FROM live_session
WHERE status = 0
ORDER BY prepare_deadline_at, id;
```

## 九、新增定时任务时的约束

新增任务应继续在 `initialize.Timer()` 统一注册，并明确：

- 唯一 Cron 名称；
- 周期和时区；
- 扫描表及索引；
- 每轮批量上限；
- 是否允许同一进程重叠；
- 多实例如何竞争处理权；
- 外部调用超时；
- 失败重试和幂等规则；
- 日志与人工排查方式。

不能只用进程内 `goroutine` 或内存标记承载必须可靠执行的任务；服务重启后仍需能够从数据库状态恢复。
