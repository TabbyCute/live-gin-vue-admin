# 直播间关闭流程

本文说明当前系统中主播主动结束、管理员结束、意外断流超时、SRS 强制断流、失败重试和最终结算的完整流程。本文以 `live_room`、`live_session` 和当前 Go 服务实现为准。

## 一、核心原则

直播结束分成两个事实：

1. 业务服务已经收到结束请求；
2. SRS 已经确认发布流停止，业务已经完成最终结算。

因此使用以下状态：

| `live_session.status` | 状态 | 含义 |
|---:|---|---|
| `0` | 准备中 | 正在等待首次有效 `on_publish`，或已收到回调但 SRS 尚未取得有效视频宽高 |
| `1` | 直播中 | SRS 已确认发布流活跃且取得有效视频宽高，或意外断流后仍处于重连窗口 |
| `2` | 结束中 | 已接受结束请求，正在停止 SRS 发布流或等待重试 |
| `3` | 已结束 | 已确认发布流停止并完成最终结算 |
| `4` | 已取消 | 准备中的场次在真正开播前取消 |
| `5` | 失败 | 因系统或业务异常退出活动状态 |

`live_room.live_status` 对应为：`0`未开播、`1`准备中、`2`直播中、`3`结束中。

数据库是直播业务状态的最终可信来源。Redis 当前不保存场次状态，也不参与结束任务认领。SRS 是媒体连接实际状态的来源。

## 二、关闭流程总览

```text
主播主动结束 / 管理员指定场次结束
                │
                ▼
数据库事务：Living → Ending
记录结束原因、结束时间和首次重试时间
                │
                ▼
事务提交后认领数据库租约
                │
                ▼
查询 SRS 发布流并强制断开 publish.cid
        ┌───────┴────────┐
        │                │
   成功或流不存在      失败或超时
        │                │
        ▼                ▼
幂等最终结算       保持 Ending
Ending → Ended     记录错误和下次重试时间
                         │
                         ▼
                    定时任务接管
```

SRS 断流使用其 HTTP API：先取得发布流的 `publish.cid`，再调用 `DELETE /api/v1/clients/{cid}`。场次保存最近一次发布回调中的 `stream_id`；该 ID 可用时优先按 ID 查询，SRS 重启或 ID 失效时再按 `vhost + app + stream` 分页查找。

## 三、主播主动结束

接口：

```http
POST /api/v1/app/live/room/session/end
Authorization: Bearer <APP JWT>
```

接口不接收场次号，服务端根据 APP JWT 找到主播、唯一直播间和 `current_session_id`。

### 1. 准备中的场次

如果场次仍为 `Preparing` 且尚未收到发布连接：

- 直接修改为 `Cancelled`；
- 写入结束原因“主播结束”；
- 清除 `live_room.current_session_id`；
- 房间修改为未开播；
- 不调用 SRS；
- 不累计主播直播次数和直播时长。

如果 `Preparing` 场次已经保存了 SRS 发布连接，只是仍未取得视频宽高，则不能直接清理数据库：先进入 `Ending` 并尝试断开 SRS 发布端；确认流已停止后再结算为 `Cancelled`。停止失败时保留房间和活动场次，由结束任务退避重试，避免媒体端仍在推流却允许创建下一场。

超过 `prepare_deadline_at` 且从未收到发布连接时，统一生命周期任务使用结束原因 `6`（准备开播超时）直接取消。收到发布连接后另由 `stream_ready_deadline_at` 控制流就绪等待；默认 15 秒仍未取得有效宽高时，也使用结束原因 `6`，但必须先执行上述安全断流流程。

### 2. 直播中的场次

数据库事务内按照 `anchor → room → session` 顺序加锁，然后：

- `live_session.status = Ending`；
- `live_room.live_status = Ending`；
- `end_reason = 1`，表示主播主动结束；
- `ended_at =` 收到结束请求的毫秒时间戳；
- 清除 `reconnect_deadline_at`，不再允许重连；
- 写入 `stop_requested_at`；
- 设置 `stop_next_retry_at`，使该场次可以被认领；
- 保留 `current_session_id`，结束完成前不能创建下一场。

事务提交后，当前请求立即尝试认领该场次并调用 SRS。网络请求不会放在数据库事务中，避免 SRS 超时长期占用数据库锁。

SRS 返回成功，或者查询确认发布流已经不存在时，接口会在返回前直接完成最终结算。如果 SRS 失败或超时，结束意图仍然已经持久化，接口按“请求已接受”处理，场次保持 `Ending`，后续由定时任务重试。

### 3. 幂等行为

- 场次已经是 `Ending`：不重复修改结束原因，只在到达重试时间且成功取得租约时再次处理；
- 定时任务刚好完成结算并清除了当前场次：主播再次点击结束按成功处理；
- 已经 `Ended`：不会再次累计主播统计；
- 用户快速重复点击不会产生新的场次或重复结算。

## 四、管理员结束和封禁相关流程

管理员指定场次结束接口使用与主播主动结束相同的同步流程，只是：

- 通过内部场次 ID 精确定位；
- `end_reason = 2`；
- 管理员填写的原因写入 `failure_reason`；
- 进入 `Ending` 后同步尝试调用 SRS，失败由定时任务接管。

后台禁用直播间、封禁主播、关闭开播权限或将主播调整为高风险时，为保证权限状态和直播状态在同一个业务事务中落库，会把直播中的场次改为 `Ending`。这些事务完成后，由定时任务取得租约并执行 SRS 断流。没有发布连接的准备场次直接取消；已有发布连接但尚未取得宽高的准备场次同样先进入 `Ending` 并安全断流。

`Ending` 状态本身也会使新的 `on_publish` 校验失败，因此旧推流断开后不能使用原场次重新连接。管理员封禁等场景还会通过房间或主播权限阻止再次准备开播。

## 五、SRS 响应如何处理

SRS 控制逻辑位于 `server/internal/srs`，业务层不会直接解析 SRS JSON。

### 成功

同时满足以下条件才属于正常 API 成功：

- HTTP 状态为 2xx；
- JSON 响应中的 `code = 0`。

下列情况按“发布流已经停止”处理，可以直接最终结算：

- 没有找到匹配的发布流；
- 找到了流，但 `publish.active = false`；
- 要删除的发布客户端已经不存在；
- `DELETE /api/v1/clients/{cid}` 成功。

SRS 7 对不存在的资源仍可能返回 HTTP 200：查询不存在的 stream 返回 `code = 2048`，
查询或删除不存在的 client 返回 `code = 2049`。客户端会把这两个明确的“不存在”业务码与 HTTP 404
统一处理：stream ID 失效时继续按 `vhost + app + stream` 查找，确认没有匹配流后才结算；client 已不存在则按幂等成功处理。

### 失败或超时

以下情况不会把场次修改为 `Ended`：

- HTTP 请求超时或连接失败；
- SRS 返回非 2xx；
- SRS JSON `code != 0`，但上述明确表示资源不存在的 `2048/2049` 除外；
- 响应无法解析；
- 发布流存在但缺少有效 `publish.cid`。

失败信息最多保存 500 个字符到 `stop_last_error`。场次继续保持 `Ending`，使用有上限的指数退避安排下一次重试。

超时属于“结果未知”，不能直接认为断流失败或成功。下一次任务会重新查询 SRS：如果流已不存在，就完成结算；如果仍存在，再次强制断流。

## 六、为什么 `on_unpublish` 不处理主动结束

当前约定是：`on_unpublish` 只负责直播中的意外断流和重连窗口，不负责推进主动结束。

处理规则：

| 收到回调时的状态 | 处理方式 |
|---|---|
| `Preparing`，连接身份匹配 | 清除当前 SRS 连接和流就绪探测字段，继续保持准备中，允许在准备期限内重新推流 |
| `Living`，尚未等待重连 | 记录 `last_unpublish_at`、增加断流次数、设置重连截止时间 |
| `Living`，已经等待重连 | 重复回调，幂等忽略，不延长截止时间 |
| `Ending` | 幂等忽略，不结算、不修改重连字段 |
| 其他状态 | 幂等忽略 |

主动结束是否成功只根据同步 SRS HTTP API 结果和定时扫描的 SRS 查询结果判断。这样不会依赖回调顺序，也不会因为迟到或重复的 `on_unpublish` 触发重复结算。

对于 `Living`，还必须先核对回调的 `server_id + client_id + stream_id` 是否属于当前保存的发布连接。重连后旧连接迟到的 `on_unpublish` 会被忽略，不能让新连接错误进入重连等待。

## 七、意外断流和重连超时

意外 `on_unpublish` 不会立即结束场次：

1. 场次继续保持 `Living`；
2. 设置 `reconnect_deadline_at = 当前时间 + reconnect-window-seconds`；
3. 重连窗口内收到合法 `on_publish`，清除重连截止时间并继续原场次；
4. 超过截止时间仍未重连，由定时任务把场次改为 `Ending`；
5. `ended_at` 使用最后一次实际断流时间，最终重连等待窗口不计入直播时长；
6. 独立的 `LiveSessionStop` 任务查询 SRS，确认流不存在或成功断开后完成结算。

## 八、定时扫描流程

数据库表结构就绪后会立即补偿执行一次 `ProcessPendingSessions` 和 `ProcessEndingSessions`，之后默认每 5 秒由两个独立任务分别执行。任务只扫描 `live_session`，不全表遍历 `live_room`；SRS 故障只会拖慢收尾任务，不会阻塞准备/重连超时扫描。

第一类查询是准备开播超时：

```sql
WHERE status = 0
  AND srs_stream_id = ''
  AND prepare_deadline_at <= 当前时间
ORDER BY prepare_deadline_at, id
LIMIT 批量大小
```

使用索引：

```text
(status, prepare_deadline_at)
```

命中的场次通过房间、场次锁与并发 `on_publish` 竞争：超时取消先提交时，发布回调会被拒绝；发布回调先提交时会写入 `srs_stream_id`，本扫描不再直接取消，改由流就绪任务等待真实宽高。`prepare_deadline_at = 0` 且没有发布连接的升级遗留准备场次也会在首次扫描时安全取消。

第二类查询是重连超时：

```sql
WHERE status = 1
  AND reconnect_deadline_at > 0
  AND reconnect_deadline_at <= 当前时间
ORDER BY reconnect_deadline_at, id
LIMIT 批量大小
```

使用索引：

```text
(status, reconnect_deadline_at)
```

第三类查询是结束中重试：

```sql
WHERE status = 2
  AND stop_next_retry_at <= 当前时间
ORDER BY stop_next_retry_at, id
LIMIT 批量大小
```

使用索引：

```text
(status, stop_next_retry_at)
```

历史上大量 `Ended` 场次不会进入查询范围。查询只返回 ID，随后按主键读取场次和房间，因此扫描成本很低；主要耗时来自真正需要执行的 SRS HTTP 请求。

## 九、人工请求和定时任务同时执行

系统不在调用 SRS 期间持有数据库事务，而是通过条件更新取得处理租约：

```sql
UPDATE live_session
SET stop_attempts = stop_attempts + 1,
    stop_next_retry_at = 租约截止时间
WHERE id = ?
  AND status = 2
  AND stop_next_retry_at <= 当前时间;
```

只有 `RowsAffected = 1` 的执行者可以调用 SRS。其他人工请求、同进程扫描任务或其他服务实例会直接跳过。

租约时间为 SRS HTTP 超时时间再加 2 秒。它解决以下情况：

- 主播点击结束时，定时任务刚好开始扫描；
- 主播连续点击结束；
- 多个服务实例同时运行扫描任务；
- 调用 SRS 的进程崩溃：租约到期后其他任务可以接管。

单进程定时器还使用 `TryLock` 禁止同一任务重叠执行；数据库租约负责跨进程、跨实例互斥。

## 十、最终结算内容

只有确认 SRS 发布流停止后，才在一个数据库事务中执行：

- `live_session.status: Ending → Ended`；
- 计算并写入 `duration_ms = ended_at - started_at`；
- 写入 `stats_finalized_at`；
- 清空停止重试时间和最近错误；
- `live_room.live_status = Offline`；
- 清空 `live_room.current_session_id` 和 `live_started_at`；
- `live_room.last_session_id` 指向本场；
- 主播累计直播次数加 1；
- 主播累计直播时长增加本场时长；
- 主播累计观看量增加本场观看量；
- 更新主播历史最高在线人数；
- 写入主播最近一次直播结束时间。

最终结算先锁主播、再锁房间、最后锁场次。若场次已经是 `Ended`，直接幂等返回，因此同步请求和扫描任务不能重复累计。

## 十一、停止控制字段

`live_session` 新增或使用以下内部字段，均不返回给 APP 和公开接口：

| 字段 | 说明 |
|---|---|
| `prepare_deadline_at` | 准备开播截止时间；首次有效发布或取消后清零 |
| `srs_server_id` | 最近一次有效发布回调的 SRS 实例标识 |
| `srs_stream_id` | 最近一次有效发布回调的流标识，优先用于 API 查询 |
| `srs_client_id` | 最近一次有效发布回调的客户端标识，保留追踪用途 |
| `srs_vhost` | 最近一次有效发布使用的 vhost |
| `srs_app` | 最近一次有效发布使用的 app |
| `stop_requested_at` | 场次进入结束中的时间 |
| `stop_attempts` | SRS 停止推流累计尝试次数 |
| `stop_next_retry_at` | 下次重试时间；处理中时同时作为租约截止时间 |
| `stop_last_error` | 最近一次失败原因 |

## 十二、配置

```yaml
live:
  reconnect-window-seconds: 20
  prepare-timeout-seconds: 120
  stream-ready-timeout-seconds: 15
  stream-ready-scan-interval-seconds: 1
  stream-ready-retry-base-seconds: 1
  stream-ready-retry-max-seconds: 4
  end-scan-interval-seconds: 5
  end-scan-batch-size: 100
  end-stop-concurrency: 8
  end-retry-base-seconds: 5
  end-retry-max-seconds: 60
  srs:
    app: live
    http_apis: http://127.0.0.1:1985
    api-username: admin
    api-password: "从环境变量注入"
    api-request-timeout-seconds: 3
```

- `http_apis` 可以配置为 SRS 地址根路径，也可以直接以 `/api/v1` 结尾；客户端会统一规范化；
- 用户名为空时不发送 Basic Auth；
- 生产环境应限制 SRS HTTP API 的网络访问，并通过环境变量提供密码；
- 批量大小最大限制为 1000，避免错误配置一次加载过多任务；
- `end-stop-concurrency` 控制单实例同时请求 SRS 的数量，小于 1 按 8、最大限制 64；
- 重试间隔默认按照 5、10、20、40、60、60……秒递增。

生产配置当前关闭了 GORM AutoMigrate，部署本功能前必须执行 `documents/live_room_session.sql` 中针对存量 `live_session` 的新增字段，以及 `idx_live_session_prepare_timeout`、`idx_live_session_end_retry` 索引升级；开发环境启用 AutoMigrate 时会自动补齐。

## 十三、运维排查

场次长时间处于 `Ending` 时，首先检查：

```sql
SELECT id, session_no, status, end_reason, ended_at,
       srs_server_id, srs_stream_id, srs_client_id,
       stop_requested_at, stop_attempts,
       stop_next_retry_at, stop_last_error
FROM live_session
WHERE status = 2
ORDER BY stop_next_retry_at, id;
```

常见原因：

- `live.srs.http_apis` 未配置或配置错误；
- Go 服务无法访问 SRS HTTP API；
- SRS API Basic Auth 账号或密码错误；
- 反向代理没有放行 `GET /streams` 或 `DELETE /clients/{cid}`；
- SRS 返回非零业务错误码；
- 定时任务未启动；
- 服务器时间偏差导致下一次重试时间尚未到达。

不要直接把所有 `Ending` 批量修改成 `Ended`。应先确认 SRS 发布流已经停止，否则可能出现数据库显示已结束但媒体仍在推流的状态不一致。
