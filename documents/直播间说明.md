# 直播间、直播场次、接口字段来源与问题排查说明

本文以当前后端代码中的 `LiveRoom`、`LiveSession`、响应 DTO 和 Service 查询为准，说明：

- `live_room` 与 `live_session` 每个字段的含义；
- 主播审核通过后，直播间如何创建；
- 从准备开播、SRS 推流、短暂断流重连到最终结算的完整流程；
- APP、公开端、SRS 回调和管理后台有哪些接口；
- 每个返回字段究竟来自哪张数据库表、服务端运行时计算，还是 Redis；
- 出现“有主播但没有房间”“列表看不到直播”“数据不更新”等问题时如何排查。

相关主播身份、审核、封禁和开播权限说明见 [主播身份说明.md](./主播身份说明.md)。
从准备开播到最终结算的接口操作顺序见 [主播开播流程说明.md](./主播开播流程说明.md)。

## 最重要的结论（先读）

1. 当前核心关系是：

   ```text
   live_anchor 1:1 live_room 1:N live_session
   ```

   - `live_anchor`：主播身份、审核、权限和主播累计统计；
   - `live_room`：一个主播唯一直播间的长期配置和当前活动状态；
   - `live_session`：一场逻辑直播一条记录，保存历史时间、结束原因和本场统计。

2. **当前直播间和直播场次接口没有从 Redis 读取任何业务返回字段。**

   - 正在直播列表直接查询 MySQL 的 `live_room + live_anchor + live_session`；
   - 在线人数、点赞数、礼物数等当前是可信统计服务通过内部接口写入 `live_session` 后，再从 MySQL 返回；
   - `publishToken` 是准备开播时生成的 pt V1 加密凭证，不来自数据库，也不来自 Redis；数据库只保存最终 Token 的 SHA-256 哈希；
   - `pushUrl`、`playUrl` 由配置和 `stream_name` 在服务端拼接，不来自数据库完整字段，也不来自 Redis；
   - 分页的 `page`、`pageSize` 来自请求，`total` 来自 SQL `COUNT`。

3. Redis 虽然是整个项目可用的基础设施，后台 JWT 在部分配置下也可能使用 Redis，但这与本文直播间业务响应无关。**不能把当前接口中的在线人数或直播状态理解成 Redis 实时值。**

4. APP 和公开端不暴露 `live_room.id`、`live_room.anchor_id`、`live_room.current_session_id`、`live_room.last_session_id`、`live_session.id`、`room_id`、`anchor_id`。客户端使用：

   - `roomNo`：直播间对外编号；
   - `anchorNo`：主播对外编号；
   - `sessionNo`：直播场次对外编号。

   内部主键只在管理后台或服务端关联中使用。

5. 主播申请审核通过时，会在同一个数据库事务内确保创建唯一直播间。默认：

   - `room_no = live_anchor.anchor_no`；
   - `stream_name = live_anchor.anchor_no`；
   - 标题为“主播昵称 + 的直播间”；
   - 分类和封面分别取 `live_anchor.category_id`、`live_anchor.cover`；
   - 房间正常、未开播、公开可见。

   管理员以后可以修改 `room_no`，但不会同步修改稳定推流名 `stream_name`。

6. 审核通过只创建直播间，**不会创建 `live_session`、不会签发推流凭证，也不会自动开启 `live_anchor.live_permission`**。主播真正准备开播时才创建场次。

## 字段来源标识

后文接口字段表使用以下来源标识：

| 来源标识 | 含义 |
|---|---|
| 数据库直出 | 直接读取某张表的某个字段 |
| 数据库关联 | 通过外键或当前指针，从另一张表补充字段 |
| SQL 计算 | 例如 `COUNT(*)` 或分页查询结果 |
| 请求参数 | 客户端本次请求携带的值 |
| 服务端计算 | Go 服务根据数据库结果组合、判断或计算 |
| 运行时生成 | 随机数、UUID、当前时间等本次运行产生的值 |
| 配置拼接 | 从 YAML 配置读取基础地址，再和数据库字段拼接 |
| Redis | 从 Redis 读取；当前本文涉及的业务字段均没有这一来源 |

所有时间戳字段除 `createdAt`、`updatedAt` 外，当前均为 **Unix 毫秒时间戳**；值为 `0` 通常表示尚未发生、未记录或当前不适用。

| 字段 | 回答的问题 | 示例 |
|---|---|---|

| 值 | 常量 | 说明 |
|---:|---|---|

### `live_room` 的约束和索引语义

- `uk_live_room_no`：保证 `room_no` 唯一；
- `uk_live_room_anchor`：保证一个主播只有一个直播间；
- `uk_live_room_stream`：保证 SRS `stream_name` 唯一；
- 发现列表索引围绕 `live_status`、`status`、`recommend_weight`、`live_started_at`；
- 分类发现索引围绕 `category_id`、`live_status`、`status`、`recommend_weight`；
- `updated_at` 没有被用作直播发现排序，因为修改标题或封面也会更新它。

## `live_session` 表字段总览

`live_session` 保存一次逻辑直播的事实记录。主播每次调用“准备开播”创建一条准备中场次；短暂断流并在重连窗口内恢复时继续使用原场次，不创建第二条记录。

### 什么是“活动场次”

“活动场次”不是另一张表，也不单指“正在直播”，而是指一条**尚未进入最终状态、仍然占用直播间的 `live_session` 记录**。

| `live_session.status` | 状态 | 是否属于活动场次 | 原因 |
|---:|---|---|---|
| `0` | 准备中 | 是 | 已创建场次和推流凭证，正在等待主播推流 |
| `1` | 直播中 | 是 | 正在推流，或者短暂断流后仍处于重连窗口 |
| `2` | 结束中 | 是 | 正在停止、清理和结算，尚不能创建下一场 |
| `3` | 已结束 | 否 | 已完成最终结算 |
| `4` | 已取消 | 否 | 在成功开播前已经取消 |
| `5` | 失败 | 否 | 已经失败并退出活动状态 |

活动场次主要用于：

- 确定主播和直播间当前正在操作哪一场直播；
- 防止主播重复点击准备开播，产生多条并行场次；
- 让 SRS 的发布流、断流和重连回调找到应该更新的 `live_session`；
- 承载本场开始时间、断流次数、重连截止时间和统计快照；
- 保证旧场次完成停止和结算后，直播间才能开始下一场。

系统使用两层机制管理活动场次：

| 机制 | 作用 |
|---|---|
| `live_room.current_session_id` | 应用层快速指向当前活动场次的 `live_session.id`；值为 `0` 表示房间当前没有活动场次 |
| `live_session.active_room_id` | 数据库生成列；状态为 `0/1/2` 时自动等于 `room_id`，并通过唯一索引从数据库层保证一个房间最多只有一条活动场次 |

典型变化过程：

```text
主播准备开播
  -> 创建 live_session，status = 0
  -> live_room.current_session_id 指向该场次

SRS 收到有效推流
  -> live_session.status = 1

主播下播、管理员强制结束或系统准备结算
  -> live_session.status = 2

最终结算完成
  -> live_session.status = 3
  -> live_room.last_session_id 指向该场次
  -> live_room.current_session_id = 0
```

`last_session_id` 不参与“活动场次”互斥，它只是一个只读加速指针：公开详情在没有活动场次时通过它按 `live_session.id` 主键读取最近一次已结束直播，避免每次请求执行 `ORDER BY ... LIMIT 1`。

因此，“没有正在推流”不一定等于“没有活动场次”。例如准备中、结束中，以及短暂断流等待重连的场次，仍然是活动场次；这时再次调用准备开播会返回“直播间已有活动场次”。

| `cover_url` | `CoverURL` / `coverUrl` | `varchar(500)`，默认 `''` | 本场封面快照 | APP 本人、后台、SRS 发布回调响应 |

当前 `live_session` 没有独立保存可查询的 `room_no` 或 `anchor_no` 快照列。新生成的 `session_no` 字符串会嵌入创建当时的 `anchorNo` 和 `roomNo`，但场次接口单独返回的 `roomNo`、`anchorNo` 仍是查询时分别从当前 `live_room.room_no`、`live_anchor.anchor_no` 补充的。因此管理员修改房间号后：

- 已存在的 `sessionNo` 不变，其中仍保留创建时使用的编号文本；
- 历史场次响应中独立的 `roomNo` 字段会显示当前新房间号；
- 业务查询和关联仍应使用数据库字段，不应通过拆分 `sessionNo` 代替正式字段。

### 场次状态和数据库唯一兜底字段

| 数据库字段 | Go 字段 / 接口字段 | 类型 / 默认值 | 解释 | 返回范围 |

| 值 | 常量 | 说明 |

| `1` | `LiveSessionLiving` | 已收到有效推流，处于直播中；短暂断流等待重连时仍保持此状态 |
| `2` | `LiveSessionEnding` | 正在结束和结算；这是可观察、可恢复的中间状态 |
| `3` | `LiveSessionEnded` | 已完成最终结算 |
| `4` | `LiveSessionCancelled` | 准备中的场次在真正开播前被取消，不计入已完成直播累计 |
| `5` | `LiveSessionFailed` | 系统或业务异常导致场次失败；当前已预留状态，现有主流程不会主动写入该状态 |

### 时间和断流重连字段

| 数据库字段 | Go 字段 / 接口字段 | 类型 / 默认值 | 解释 | 返回范围 |
|---|---|---|---|---|
| `prepare_deadline_at` | `PrepareDeadlineAt` / `prepareDeadlineAt` | `bigint`，默认 `0` | 准备开播截止时间；首次有效发布或取消后清零，升级遗留的 `0` 会由启动扫描清理 | APP 本人、后台、准备接口 |
| `started_at` | `StartedAt` / `startedAt` | `bigint`，默认 `0` | 第一次收到有效 SRS `on_publish` 的毫秒时间戳；准备中为 `0` | APP 本人、后台、SRS 发布回调响应 |
| `publish_ip` | `PublishIP` / 后台 `publishIp` | `varchar(45)`，默认 `''` | 本场首次成功发布流 IP；预留 IPv4/IPv6。只允许管理后台读取，不进入 APP、公开接口或通用场次响应 | 仅后台 |
| `ended_at` | `EndedAt` / `endedAt` | `bigint`，默认 `0` | 逻辑场次结束时间。正常主动结束取请求时间；断流超时通常取最后一次 `on_unpublish` 时间 | APP 本人、后台、SRS 发布回调响应 |

| `disconnect_count` | `DisconnectCount` / `disconnectCount` | `int unsigned`，默认 `0` | 本场累计有效断流次数；同一次重复 `on_unpublish` 不重复累计，也不延长窗口 | APP 本人、后台、SRS 发布回调响应 |

例如：

```text
20:00:00 首次开播
20:30:00 断流
20:30:20 重连成功
21:00:00 主播下播
```

最终 `duration_ms` 为约 60 分钟，包含中途的 20 秒短暂断流。若 20:30 断流后一直没有重连，并因超时结束，则 `ended_at` 使用 20:30 的最后断流时间，最终重连等待窗口不计入时长。

### `live_session` 的约束和索引语义

- `uk_live_session_no`：保证 `session_no` 唯一；
- `uk_live_session_active_room`：基于生成列 `active_room_id`，从数据库层保证同一 `room_id` 最多一个状态为 `0/1/2` 的场次；
- `idx_live_session_room_created` 当前实际只标记了 `room_id`；虽然索引名带有 `created`，Model 并未把 `created_at` 加入该复合索引；
- 主播历史索引：`anchor_id + started_at DESC`；
- 分类历史索引：`category_id + started_at DESC`；
- 准备超时扫描索引：`status + prepare_deadline_at`；
- 重连扫描索引：`status + reconnect_deadline_at`。

## 主播审核通过到开播、断流和结算的完整流程

### 1. 审核通过时创建直播间

后台把 `live_anchor.apply_status` 审核为 `2` 后，系统在同一事务内执行“确保房间存在”：

| 新房间字段 | 初始值来源 |
|---|---|
| `live_room.room_no` | `live_anchor.anchor_no` |
| `live_room.anchor_id` | `live_anchor.id` |
| `live_room.category_id` | `live_anchor.category_id` |
| `live_room.title` | `live_anchor.nickname + "的直播间"` |
| `live_room.cover_url` | `live_anchor.cover` |
| `live_room.stream_name` | `live_anchor.anchor_no` |
| `live_room.status` | `1`，正常 |
| `live_room.status_changed_at` | 服务端当前毫秒时间 |
| `live_room.live_status` | `0`，未开播 |
| `live_room.visibility` | `1`，公开 |

系统启动时还会批量补齐“历史上已经审核通过但没有直播间”的异常数据。该补偿过程是幂等的。

### 2. 主播修改直播间资料

调用 `POST /api/v1/app/live/room/save` 后更新：

- `live_room.category_id`；
- `live_room.title`；
- `live_room.cover_url`；
- `live_room.notice`；
- `live_room.visibility`。

该接口要求主播申请已通过且主播身份正常，并校验分类是否可用。对于升级遗留的缺房间数据，保存时也会尝试补建房间。

### 3. 准备开播

调用 `POST /api/v1/app/live/room/session/prepare` 时：

1. 重新从数据库检查主播申请、账号状态、开播权限、风险等级等资格；
2. 检查房间 `status = 1`；
3. 校验 `live_category`；
4. 确认没有活动场次；
5. 按 `yyyyMMddHHmmssSSS-anchorNo-roomNo` 生成 `sessionNo`；
6. 组装包含场次、SRS 应用、vhost、流名、凭证代数和有效期的 pt V1 载荷，用 AES-256-GCM 加密后生成 `publishToken`；
7. 创建状态为准备中的 `live_session`；
8. 写入 `prepare_deadline_at = 当前时间 + prepare-timeout-seconds`；
9. 更新 `live_room` 当前标题、封面、分类、可见范围、密钥哈希、版本和当前场次指针；
10. 返回推流地址、播放地址和准备截止时间。

此时：

```text
live_room.live_status = 1
live_session.status = 0
live_session.prepare_deadline_at > 0
live_session.started_at = 0
```

### 4. SRS 收到推流

SRS 调用 `POST /api/v1/app/live/hook/publish`，服务端会：

- 用 `stream` 查询 `live_room.stream_name`；
- 从 `param` 提取 `pt`（暂时兼容旧 `token`），使用 `live.publish-token-key` 解密并校验 GCM 完整性、版本、作用域、时间窗口、场次、app、vhost、stream 和凭证版本，同时计算 SHA-256 后和 `live_room.publish_secret_hash` 常量时间比较；
- 重新检查主播和房间状态；
- 首次发布时把场次改为直播中并写入 `started_at`；
- 首次发布前再次校验 `prepare_deadline_at`；超时后即使扫描尚未执行也拒绝开播；
- 首次发布成功后清零 `prepare_deadline_at`；
- 更新 `live_room.live_status = 2`、`live_room.live_started_at = live_session.started_at`；
- 更新 `live_anchor.last_live_at`。

### 5. SRS 断流与短暂重连

SRS 调用 `POST /api/v1/app/live/hook/unpublish` 时不会立刻结束场次，而是：

```text
last_unpublish_at = 当前时间
reconnect_deadline_at = 当前时间 + reconnect-window-seconds
disconnect_count = disconnect_count + 1
```

当前开发配置的重连窗口为 120 秒；如果配置值小于等于 0，代码使用 20 秒兜底。

- 截止前重新收到有效 `on_publish`：清空 `reconnect_deadline_at`，继续原 `sessionNo`；
- 截止后仍未重连：调用 `ProcessPendingSessions` 时把场次置为结束中，结束原因为断流超时；
- 重复收到同一次 `on_unpublish`：幂等忽略，不重复计数、不延长窗口。
- 重连后旧连接迟到的 `on_unpublish`：根据 `server_id + client_id + stream_id` 幂等忽略，不影响新连接。

### 6. 主播或管理员结束直播

- 准备中结束：直接变为已取消 `4`，清理房间当前场次；
- 直播中结束：先变为结束中 `2`，房间变为结束中 `3`，事务提交后同步尝试 SRS 断流；
- SRS 断流成功或确认流已不存在：立即完成最终结算；
- SRS 失败或超时：保持结束中，由内置定时任务按退避时间重试；
- 重复结束采用幂等处理，不重复断流或重复累计统计。

主播端不传场次编号，服务端根据 APP JWT 和 `live_room.current_session_id` 结束当前活动场次；后台管理员使用内部 `sessionId`，并填写结束原因。

### 7. 场次最终结算

内置 `LiveSessionLifecycle` 定时任务默认每 5 秒执行 `ProcessPendingSessions`：

1. 表结构就绪后启动时立即补偿一次，之后按默认 5 秒周期运行；
2. 找出准备开播超时的场次，将其取消并释放房间；
3. 找出超过重连截止时间的直播中场次，将其标记为结束中；
4. 找出已经到达重试时间的结束中场次，通过数据库租约认领；
5. 查询并停止 SRS 发布流；
6. SRS 成功或流不存在时最终结算，失败则记录错误并退避重试。

结算时：

- `live_session.status = 3`；
- 计算 `duration_ms`；
- 清空 `reconnect_deadline_at`；
- 写入 `stats_finalized_at`；
- 把 `live_room.last_session_id` 更新为本场内部 ID；
- 清空 `live_room.current_session_id`、`live_started_at`，恢复 `live_status = 0`；
- 累加 `live_anchor.total_live_count`、`total_live_duration_ms`、`total_view_count`；
- 刷新 `live_anchor.max_online_count`、`last_live_end_at`。

开发配置中 `system.router-prefix = /api`，所以完整路径如下。若其他环境修改了路由前缀，应把下面的 `/api` 替换为实际配置值。

### 统一响应外层

安全注意：

- `publishToken` 不透明字符串只在本次准备响应中返回，不写入数据库和 Redis；
- 数据库只保存 `live_room.publish_secret_hash`；
- 如果 `push-base-url` 或 `play-base-url` 没有配置，对应返回值为空字符串；
- 不要把 `publishToken` 写入前端日志、监控日志或错误上报；
- 重新准备新场次会轮换凭证，旧凭证哈希被覆盖。

SRS 连接配置：

- `live.srs.app` 保存 SRS 流应用名；
- `live.srs.http_apis` 保存 SRS HTTP API 基础地址；
- 这两个字段当前只完成配置接入，直播服务尚未主动调用 SRS HTTP API。

`sessionNo` 唯一性规则：

- 格式为 `yyyyMMddHHmmssSSS-anchorNo-roomNo`，例如 `20290806135612345-1500001-1500001`；
- 时间部分使用 17 位毫秒时间，而不是示例中只有分钟精度的 12 位时间；否则同一主播在同一分钟取消后重新准备会产生重复编号；
- 生成前会连同软删除记录一起检查 `live_session.session_no`；若同一毫秒发生碰撞，顺延逻辑毫秒后重试；
- 同一直播间的准备事务会锁定 `live_room`，避免本服务并发生成相同编号；
- 数据库唯一索引 `uk_live_session_no` 是最终兜底；
- `session_no` 长度为 `varchar(96)`，可以容纳最长 32 字符的 `anchorNo` 和 `roomNo`。

#### 公开详情的场次选择逻辑

公开详情始终返回直播间资料和完整 `anchorInfo`。`latestSession` 按以下优先级选择：

```text
live_room.current_session_id > 0
  -> 返回当前准备中、直播中或结束中的活动场次

live_room.current_session_id = 0 且 live_room.last_session_id > 0
  -> 返回最近一次真正开播并完成结算的场次

两个指针都为 0
  -> latestSession 返回空对象 {}，表示主播从未完成过直播
```

数据库使用一次主键关联完成选择：

```sql
LEFT JOIN live_session AS ls
  ON ls.id = CASE
    WHEN live_room.current_session_id > 0 THEN live_room.current_session_id
    ELSE live_room.last_session_id
  END
 AND ls.deleted_at IS NULL
```

`last_session_id` 只在实际开播的场次完成结算时更新。准备后取消、准备失败不会覆盖它，因此“最近一次直播”不会错误地变成一次没有真正开播的尝试。

- `liveStatus` -> `live_room.live_status`。

### 管理后台直播场次接口总览

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/v1/admin/live/session/list` | 分页查询直播场次 |
| `GET` | `/api/v1/admin/live/session/detail?sessionId=...` | 按内部主键查询场次详情 |
| `POST` | `/api/v1/admin/live/session/end` | 强制结束场次 |

后台场次列表/详情在通用 `LiveSessionInfo` 基础上增加：

| 返回字段 | 精确来源 | 来源类型 | Redis |
|---|---|---|---|
| `id` | `live_session.id` | 数据库直出 | 否 |
| `createdAt` | `live_session.created_at` | 数据库直出 | 否 |
| `roomId` | `live_session.room_id` | 数据库直出 | 否 |
| `anchorId` | `live_session.anchor_id` | 数据库直出 | 否 |
| `publishIp` | `live_session.publish_ip` | 数据库直出；仅后台 DTO 返回 | 否 |

其他 `sessionNo` 到 `statsFinalizedAt`（包括 `streamInfo`）的来源见“通用 `LiveSessionInfo` 字段来源”。分页字段同样来自数据库查询、SQL `COUNT` 和请求参数，不来自 Redis。

后台场次列表筛选字段：

- `sessionNo` -> `live_session.session_no LIKE`；
- `roomNo` -> 先查当前 `live_room.room_no LIKE` 得到房间 ID，再过滤 `live_session.room_id`；
- `anchorNo` -> 先查当前 `live_anchor.anchor_no LIKE` 得到主播 ID，再过滤 `live_session.anchor_id`；
- `categoryId` -> `live_session.category_id`；
- `status` -> `live_session.status`；
- `startedAtStart/startedAtEnd` -> `live_session.started_at` 毫秒时间范围。

### SRS/可信统计服务内部接口

这些接口不使用 APP JWT，也不使用后台 JWT；其来源鉴权由防火墙、负载均衡或反向代理上的真实来源 IP/CIDR 白名单完成。应用层不会信任客户端提供的 `X-Forwarded-For`，也不再要求额外 Header Token。

| 方法 | 路径 | 调用方 | 成功时 `data` |
|---|---|---|---|
| `POST` | `/api/v1/app/live/hook/publish` | SRS | `LiveSessionInfo` |
| `POST` | `/api/v1/app/live/hook/unpublish` | SRS | `{}` |
| `POST` | `/api/v1/app/live/hook/session/stats` | 可信统计服务 | `{}` |

`publish` 返回字段来源与通用 `LiveSessionInfo` 相同。`unpublish` 和 `session/stats` 只返回空对象及固定消息。发布/断流回调会接收 SRS 6.x 的 `server_id`、`service_id`、`action`、`client_id`、`ip`、`vhost`、`app`、`tcUrl`、`stream`、`param`、`stream_url`、`stream_id`；未知扩展字段也会保存在请求对象的 `Extra` 中，供后续版本使用。`publish` 会使用 `param` 中的 `pt`（暂时兼容旧 `token`）完成解密和业务字段校验，并记录首次发布 IP。当前发布连接的 `server_id + client_id + stream_id` 会参与重复/乱序回调判定，旧连接不能覆盖或断开新连接的业务状态。

## 哪些值明确不来自 Redis

| 数据 | 当前真实来源 | 说明 |
|---|---|---|
| 房间状态 | `live_room.status` | MySQL 持久化状态 |
| 当前直播状态 | `live_room.live_status` | MySQL 当前状态快照 |
| 当前活动场次 | `live_room.current_session_id` -> `live_session` | MySQL 关联 |
| 最近一次已结束直播 | `live_room.last_session_id` -> `live_session` | MySQL 主键关联；公开详情没有活动场次时使用 |
| 直播开始时间 | `live_room.live_started_at` 或 `live_session.started_at` | MySQL |
| 在线/观看统计 | `live_session.viewer_count/view_count/peak_online_count` | 统计服务写入 MySQL 的快照 |
| 点赞统计 | `live_session.like_count` | 统计服务写入 MySQL 的快照 |
| 礼物汇总 | `live_session.gift_count/gift_coin_amount/gift_user_count` | 统计服务写入 MySQL 的汇总 |
| 断流和重连窗口 | `live_session.last_unpublish_at/reconnect_deadline_at/disconnect_count` | MySQL |
| 准备开播截止时间 | `live_session.prepare_deadline_at` | MySQL；不保存到 Redis |
| 公开直播列表 | `live_room + live_anchor + live_session` JOIN | 每次请求直接查询 MySQL |
| `publishToken` | pt V1 载荷 + AES-256-GCM + Base64URL | 只有最终 Token 的哈希写入 MySQL；不写 Redis |
| `sessionNo` | 毫秒时间、`live_anchor.anchor_no`、`live_room.room_no` 组合后写入 `live_session.session_no` | 不是 Redis 自增值；唯一性由碰撞检查和数据库唯一索引共同保证 |
| `pushUrl/playUrl` | YAML 配置 + `stream_name` 拼接 | 不是缓存值 |

如果以后为了高并发增加 Redis，可以考虑缓存“瞬时在线人数、热度榜、房间心跳、短期幂等键”等，但必须定义：

- Redis 是实时源还是缓存；
- 如何定期或结束时落库；
- Redis 丢失时如何恢复；
- MySQL 与 Redis 冲突时谁为准；
- 对外字段返回实时值还是已落库快照。

在这些规则和代码真正实现前，文档与客户端都应按“当前全部业务字段以 MySQL 为准”理解。

## 常见问题排查

### 1. 主播审核通过，但后台直播间列表没有房间

正常行为是审核通过后立即能在 `/api/v1/admin/live/room/list` 查到房间。按顺序检查：

1. `live_anchor.apply_status` 是否确实为 `2`；
2. `live_room.anchor_id` 是否存在对应记录；
3. 审核事务是否因 `room_no` 或 `stream_name` 唯一冲突而整体回滚；
4. 后台列表是否携带了 `roomNo`、`anchorNo`、分类、房间状态或直播状态筛选；
5. 记录是否被软删除，即 `live_room.deleted_at` 非空；
6. 服务启动时 `BackfillApprovedAnchorRooms` 是否执行成功。

可用 SQL 思路：

```sql
SELECT a.id, a.anchor_no, a.apply_status, r.id AS room_id, r.room_no
FROM live_anchor a
LEFT JOIN live_room r
  ON r.anchor_id = a.id
 AND r.deleted_at IS NULL
WHERE a.apply_status = 2
  AND a.deleted_at IS NULL
  AND r.id IS NULL;
```

该查询有结果，表示存在“审核已通过但没有直播间”的异常数据。

### 2. 房间存在，但主播不能准备开播

依次检查：

- `live_anchor.apply_status = 2`；
- `live_anchor.status = 1`；
- `live_anchor.live_permission = 1`；
- `live_anchor.risk_level != 3`；
- `live_room.status = 1`；
- 分类存在、启用，且父分类可用；
- `live_room.current_session_id = 0`，或者它没有指向状态 `0/1/2` 的活动场次；
- 数据库唯一索引 `uk_live_session_active_room` 是否因已有活动场次而拒绝创建。

注意：审核通过会创建房间，但不会自动开启 `live_permission`。

### 3. 已准备开播，但公开列表看不到

准备完成只代表：

```text
live_room.live_status = 1
live_session.status = 0
```

公开列表只展示已收到有效 `on_publish` 后的直播中房间。继续检查：

- SRS 是否调用了 `hook/publish`；
- 部署层来源 IP 白名单是否允许实际 SRS 节点；
- 推流地址中的 `pt` 是否是本次准备返回且尚未过期的凭证；
- `live.publish-token-key` 是否与签发 pt 时使用的密钥一致；
- SRS `stream` 是否等于 `live_room.stream_name`，而不是管理员修改后的 `room_no`；
- `live_room.live_status` 是否已经为 `2`；
- `live_session.status` 是否已经为 `1`；
- 房间 `status` 是否为 `1`；
- `visibility` 是否为 `1`；
- 主播 `status` 是否为 `1`、`apply_status` 是否为 `2`。

### 4. 公开详情返回“直播间不存在”，后台却能看到房间

公开详情允许查询未开播的房间，所以“房间未开播”本身不会导致返回不存在。以下任一情况仍会查不到：

- 房间被禁用或关闭；
- 可见范围不是公开；
- 主播状态不正常或申请不是已通过；
- 房间或主播记录被软删除；
- 使用了旧 `roomNo`，而管理员已修改房间号。

如果详情能查到、公开列表却没有，先看 `liveStatus`：只有 `2` 才会进入正在直播列表。

### 5. OBS 断流一下，为什么没有生成新场次

这是预期行为。`on_unpublish` 只写入重连截止时间，窗口内重连会继续原 `sessionNo`。只有真正结束后，下次重新准备开播才创建新场次。

### 6. 断流超时后仍短暂显示直播中或结束中

内置任务默认每 5 秒处理断流超时和结束重试，因此短暂延迟属于正常现象。若长期不变化，检查：

- `LiveSessionLifecycle` 是否成功注册和运行；
- `reconnect_deadline_at` 是否大于 0 且已经到期；
- `stop_next_retry_at` 是否已经到期、`stop_last_error` 是否记录 SRS 错误；
- `live.srs.http_apis`、认证和网络是否正确；
- 场次状态是否异常；
- 数据库事务或锁是否失败。

### 7. 在线人数、点赞或礼物数一直是 0

当前查询不会从 Redis、SRS 或礼物流水临时聚合。检查可信统计服务是否持续调用：

```text
POST /api/v1/app/live/hook/session/stats
```

并检查：

- 可信统计服务是否在部署层来源 IP 白名单中；
- `sessionNo` 是否正确；
- 场次状态是否仍为 `0/1/2`；
- 请求是否传递了完整累计值；
- MySQL `live_session` 对应统计字段是否已经更新。

### 8. 管理员改了房间号，OBS 原推流地址为什么不变

这是设计行为：

- 对外房间号：`live_room.room_no`，允许后台修改；
- 稳定推流名：`live_room.stream_name`，创建后保持稳定；
- 场次号：`live_session.session_no`，每次准备开播重新生成。

这三个编号用途不同。修改 `room_no` 不会修改 `stream_name`，避免 OBS/SRS 推流入口意外变化。

### 9. 历史场次的房间号为什么跟开播时不同

因为 `live_session` 当前没有独立的 `room_no` 快照列。历史接口的 `roomNo` 是查询时从当前 `live_room.room_no` 补充的。虽然新格式 `sessionNo` 会嵌入创建时的房间号文本，但它是不可变业务编号，不应作为可查询的正式房间号字段；若业务需要明确查询开播时的房间号，仍应新增专门的快照列。

### 10. 管理后台接口报未登录或权限不足

当前后台直播管理接口挂在管理员 JWT 私有路由下。先检查：

- 是否请求 `/api/v1/admin/live/...`；
- 是否携带有效后台 token，而不是 APP Bearer token；
- 管理后台角色是否分配了对应直播管理菜单；
- 前端菜单隐藏不等同于后端业务数据不存在。

当前项目已不使用 Casbin API 级角色策略控制这些直播接口；后台仍要求登录，角色主要通过菜单分配控制可见入口。

## 对外字段和内部字段边界

### APP 和公开端可以使用

- `roomNo`；
- `anchorNo`；
- `sessionNo`；
- DTO 明确返回的房间资料、状态和统计字段。

### 只允许后台或服务端使用

- `live_room.id`、`anchor_id`、`current_session_id`、`last_session_id`；
- `live_session.id`、`room_id`、`anchor_id`；
- 管理后台以 `roomId`、`sessionId` 执行精确操作。

### 任何查询接口都不应返回

- `live_room.publish_secret_hash`；
- `publishToken` 的持久化字符串，因为系统只保存最终 Token 的 SHA-256 哈希；
- 两张表的 `deleted_at`、`extra` 等内部字段；
- 未经 DTO 白名单明确允许的完整 GORM Model。

Model 上存在 JSON 标签不代表某个接口就一定返回该字段；实际返回范围必须以 `server/model/live/response/live_room.go` 中的响应 DTO 为准。
